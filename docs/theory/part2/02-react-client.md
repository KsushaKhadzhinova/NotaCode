## Ключевая теория

### 1. Компонентный подход (лекция 01)

- **Компонент** — независимый, переиспользуемый кусок UI со своей разметкой (JSX), логикой (обработчики, состояние) и стилями.
- Идеи: «разделяй и властвуй», переиспользование, **композиция** (сложное из простого: `ProductCard` = `Image` + `Title` + `Price` + `Button`), **однонаправленный поток данных** (родитель → потомок через props).
- **Декларативность**: описываем, *каким* должен быть UI при данном состоянии, React сам обновляет DOM. Формула: **UI = f(state)**.
- Плюсы: простота поддержки, параллельная работа команды, лёгкое тестирование изолированных компонентов.
- Приложение — **дерево компонентов** с корнем `<App />`.
- Функциональные компоненты (функции + хуки) — современный стандарт; классовые (`this.state`, методы жизненного цикла) — устаревший подход.
- **Реактивное программирование** — работа с асинхронными потоками данных/событий (RxJS; в React — хуки вроде `useEffect`). Плюсы: гибкость UI, удобство асинхронщины.

### 2. Библиотеки компонентов, MUI (лекции 02–03)

- Библиотека компонентов — набор готовых стилизованных UI-элементов (кнопки, формы, таблицы, модалки). Плюсы: скорость, единый стиль (консистентность UI/UX), кросс-браузерность, адаптивность, документация, темизация.
- Обзор:
  | Библиотека | Фреймворк | Особенность |
  |---|---|---|
  | **MUI (Material UI)** | React | Google Material Design, темы, TS |
  | **Ant Design** | React | бизнес-интерфейсы, мощные таблицы/формы, TS |
  | Semantic UI | — | семантичные, понятные имена классов |
  | **Chakra UI** | React | простой API, доступность (a11y), темизация |
  | Vuetify | Vue | Material Design |
  | Tailwind UI | любая | компоненты на утилитарных классах Tailwind CSS |
  | Element UI | Vue | богатый набор, TS |
- Когда брать: нужна быстрая разработка, единообразие, адаптивность, много стандартных элементов.
- **MUI** (`npm install @mui/material @emotion/react @emotion/styled`; иконки — `@mui/icons-material`):
  - `Button` — `variant`: `contained` | `outlined` | `text`; `color`: `primary`, `secondary`, `success`, `error`, `warning`, `info`.
  - `TextField` — `label`, `variant` (`outlined`/`filled`/`standard`), `fullWidth`, `error`.
  - `Card` / `CardContent` / `Typography`.
  - `Grid container` / `Grid item` с брейкпоинтами `xs={12} sm={6} md={4}`.
  - `AppBar` + `Toolbar` + `Typography` — верхняя панель.
  - `Modal` (`open`, `onClose`) + `Box` для стилизации содержимого.
  - `Switch` + `FormControlLabel` — переключатель (например, темы).
  - Темизация: `createTheme()` → `<ThemeProvider theme={...}>`, `<CssBaseline />` сбрасывает стили браузера; точечная стилизация — проп `sx`, `styled()`.
  - Самостоятельно: система тем, Data Grid (таблицы с фильтрацией/сортировкой), MUI Icons.

### 3. JSX (лекция 04)

- JSX — синтаксическое расширение JS; Babel/сборщик превращает `<h1 className="t">Hi</h1>` в `React.createElement('h1', {className:'t'}, 'Hi')`.
- Правила:
  1. Один корневой элемент (или фрагмент `<>...</>`; с `key` — `<React.Fragment key=...>`).
  2. Все теги закрыты: `<img />`, `<br />`, `<input />`.
  3. JS-выражения в `{}`; инструкции (`if`, `for`) внутри нельзя.
  4. Атрибуты в camelCase: `className`, `htmlFor`, `tabIndex`, `onClick`, `readOnly`, `maxLength`; `aria-*` и `data-*` — как в HTML.
  5. `style` — объект: `style={{ backgroundColor: 'red' }}`.
  6. Комментарии: `{/* ... */}`.
- Условный рендеринг: тернарный `?:`, логическое `&&`, либо вычисление переменной до `return`.
- Списки: `arr.map(x => <li key={x.id}>…</li>)`; `key` уникален и стабилен; индекс — только для статичных списков.
- Защита от XSS: всё в `{}` экранируется; сырой HTML — только через `dangerouslySetInnerHTML` для доверенного контента.
- Типичные ошибки: незакрытый тег, `class` вместо `className`, два корня, забытые `{}`, рендер объекта целиком (`{user}` → ошибка, нужно `{user.name}`).

### 4. Функциональные компоненты (лекция 05)

- Функция, принимающая `props` и возвращающая JSX (или `null`). Имя — с заглавной буквы (иначе считается HTML-тегом); обычно совпадает с именем файла; `export default`.
- До React 16.8 — «stateless components»; с хуками получили состояние (`useState`, `useReducer`), эффекты (`useEffect`), контекст (`useContext`), рефы (`useRef`), мемоизацию (`useMemo`, `useCallback`).
- Композиция и `children`.
- Сравнение с классовыми: короче, нет `this`, логика переиспользуется через **кастомные хуки** (вместо HOC/render props).
- Ошибки: имя со строчной, забыт `return`, изменение props, хук в условии/цикле, мутация состояния (`state.count++`).

### 5. Props (лекция 06)

- Данные родитель → потомок; **только для чтения**; любые типы (строки, числа, массивы, объекты, функции, JSX).
- Строки — в кавычках, всё остальное — в `{}`; `<Button disabled />` ≡ `disabled={true}`.
- Деструктуризация в параметрах: `function Card({ title, children })`.
- Значения по умолчанию: параметры по умолчанию (рекомендуется) или `Component.defaultProps` (устар.). Дефолт применяется, только если prop не передан вовсе.
- `children` — содержимое между тегами (строка, элемент, массив, функция — render prop).
- Колбэки в props — связь «ребёнок → родитель»: `<Item onDelete={handleDelete} />`.
- Spread: `<User {...userProps} />` (осторожно — лишние props).
- Валидация: `prop-types` (`PropTypes.string.isRequired`, `number`, `bool`, `func`, `array`, `object`, `node`, `element`, `oneOf`, `arrayOf`, `shape`) — только в dev; альтернатива — TypeScript-интерфейсы.
- Неизменяемость → предсказуемость, быстрая проверка изменений по ссылке, нет побочных эффектов.

### 6. Хуки useState и useEffect (лекция 07)

- **Правила хуков**: вызывать только на верхнем уровне (не в условиях/циклах/вложенных функциях) и только из компонентов или кастомных хуков — порядок вызовов должен быть одинаков при каждом рендере.
- `const [state, setState] = useState(initial)`:
  - сеттер планирует перерендер;
  - **функциональное обновление** при зависимости от предыдущего: `setCount(prev => prev + 1)` (два `setCount(count+1)` подряд дают +1, а не +2);
  - **иммутабельность**: `setUser({...user, age: 26})`, `setItems([...items, x])`, `items.filter(...)`, `items.map(...)`;
  - **ленивая инициализация**: `useState(() => JSON.parse(localStorage.getItem('k')) ?? [])` — функция выполняется один раз.
- `useEffect(fn, deps)`:
  | deps | когда запускается |
  |---|---|
  | нет массива | после каждого рендера |
  | `[]` | один раз после монтирования (аналог `componentDidMount`) |
  | `[a, b]` | после первого рендера и при изменении `a` или `b` |
  - Функция очистки `return () => {...}` вызывается перед повторным запуском эффекта и при размонтировании (таймеры, подписки, слушатели, WebSocket).
  - В deps указывать **все** используемые изменяемые значения (иначе stale closure).
  - Порядок: рендер → обновление DOM → эффекты в порядке объявления.
  - Ошибки: бесконечный цикл (`setCount` внутри эффекта с `[count]`), пропущенные зависимости, мутации.
- Пример debounce-поиска: `setTimeout` 500 мс внутри эффекта с `[query]` + `clearTimeout` в очистке.

### 7. Локальное состояние (лекция 08)

- Принадлежит компоненту: приватное, изменяемое, триггер перерендера, у каждого экземпляра своё.
- **Props vs state**: источник (родитель / сам компонент), изменяемость (нет / да через сеттер), кто обновляет.
- **Single Source of Truth** — одно значение хранится в одном месте; **поднятие состояния (lifting state up)** к ближайшему общему предку, вниз — значение и колбэк (пример: конвертер °C/°F).
- Несколько `useState` (для независимых полей) vs один объект (для одной сущности; всегда `prev => ({...prev, field})`).
- Не хранить вычислимое (fullName из firstName+lastName) — считать при рендере.
- Признаки необходимости глобального состояния: prop drilling, удалённые компоненты делят данные, данные влияют на всё приложение (тема, auth). Инструменты: Context API; Redux/Zustand/MobX.
- Рекомендации: начинать с локального, сложные переходы — `useReducer`, переиспользуемая логика — кастомные хуки (`useLocalStorage`, `useForm`).

### 8. Сайд-эффекты (лекция 09)

- Сайд-эффекты: запросы, storage, таймеры, подписки, прямой DOM (фокус), интеграция сторонних библиотек. Выполняются **после** рендера, не блокируют отрисовку, с очисткой, с «честными» зависимостями.
- Асинхронный запрос: async-функцию объявить **внутри** эффекта и вызвать (сам колбэк эффекта не может быть async); состояния `loading/error/data`; `try/catch/finally`.
- Защита от обновления размонтированного компонента: флаг `isMounted`/`ignore` или **AbortController**:
  ```js
  useEffect(() => {
    const ac = new AbortController();
    fetch(url, { signal: ac.signal }).then(r => r.json()).then(setData)
      .catch(e => { if (e.name !== 'AbortError') setError(e.message); });
    return () => ac.abort();
  }, [url]);
  ```
- `setTimeout`/`setInterval` + `clearTimeout`/`clearInterval`; `addEventListener` + `removeEventListener`; `new WebSocket` + `ws.close()`; `useRef` для DOM-элемента.
- Условный эффект: `if` внутри эффекта; пропуск первого рендера через `useRef(true)`.
- **Кастомные хуки**: `useFetch(url)` → `{data, loading, error}`; `useLocalStorage(key, initial)` → `[value, setValue]` (ленивое чтение + эффект записи).
- Таблица ошибок: async без обёртки, нет очистки, нет isMounted, пустые deps при использовании props, слишком много deps (→ `useCallback`/`useMemo`), мутации.

### 9. React Router v6 (лекции 10–11)

- `npm install react-router-dom`. Клиентская маршрутизация через HTML5 History API (`pushState`/`replaceState`, событие `popstate`) — без перезагрузки страницы.
- Компоненты:
  - `BrowserRouter` (корень; альтернативы — `HashRouter` `/#/about`, `MemoryRouter` для тестов);
  - `Routes` (вместо v5 `Switch`, выбор по «лучшему совпадению», порядок не важен) и `Route path element={<X/>}` (вместо `component`/`render`);
  - `Link` (аналог `<a>` без перезагрузки), `NavLink` (активный класс/стиль: `className={({isActive}) => ...}`, проп `end` для точного совпадения);
  - `Outlet` — место рендера дочерних маршрутов во вложенном макете; `<Route index>` — маршрут по умолчанию;
  - `Navigate to="..." replace` — декларативный редирект.
- Хуки: `useParams`, `useNavigate`, `useLocation` (`pathname`, `search`, `hash`, `state`, `key`), `useMatch`.
- **SPA vs MPA**: SPA — мгновенная навигация, сохранение состояния, офлайн (PWA); минусы — SEO (нужен SSR/Next.js или пререндер), тяжёлая первая загрузка, настройка сервера (fallback на `index.html`: Nginx `try_files $uri $uri/ /index.html;`), аналитика вручную по смене `location`.
- Жизненный цикл SPA: сервер отдаёт пустой `<div id="root">` + бандл → Router читает URL → рендер страницы → клик по `Link` → `pushState` → новый компонент (+ загрузка JSON).
- Типовая структура: `src/components`, `src/pages`, `src/layouts/MainLayout.jsx` (шапка + `<Outlet/>` + подвал), `App.jsx` с маршрутами, `path="*"` → NotFound.
- Приёмы: **code splitting** (`lazy(() => import('./pages/Home'))` + `<Suspense fallback>`), передача state при навигации (`navigate('/p', {state:{from:'login'}})` → `location.state?.from`), `ScrollToTop` (эффект по `pathname`), `navigate('/dashboard', {replace:true})` после логина.

### 10. Динамические маршруты (лекция 12)

- `path="/users/:userId"`, несколько параметров `/products/:categoryId/:productId`; `const { userId } = useParams()` — **всегда строки** (`Number(userId)`).
- Загрузка данных по параметру — `useEffect(..., [userId])`, чтобы при переходе `/users/1` → `/users/2` данные обновились.
- Вложенные динамические маршруты: `/blog/:postId` c `Outlet` и детьми `comments`, `author`, `index`; параметр доступен и в детях.
- Опциональные параметры — через два маршрута (`/products` и `/products/:category`) или query-параметры.
- Query-строка: `new URLSearchParams(useLocation().search).get('page')`; кастомный `useQuery()` через `useMemo` (в v6 также есть `useSearchParams`).
- Ссылки: `<Link to={`/users/${u.id}`}>`, `navigate(`/users/${id}`)`.
- Несуществующий ресурс → `<Navigate to="/404" replace />` или `navigate('/not-found', {replace:true})` после ответа 404.

### 11. Навигация и защита маршрутов (лекция 13)

- Декларативная (`Link`, `NavLink`; `state` в `Link`; относительные пути без `/`, абсолютные с `/`) и императивная (`navigate('/x')`, `navigate(-1)`, `navigate(1)`, `{replace:true}`, `{state}`).
- Редирект на `/login` при 401 внутри эффекта.
- **PrivateRoute**:
  ```jsx
  function PrivateRoute({ children }) {
    const isAuth = !!localStorage.getItem('token');
    return isAuth ? children : <Navigate to="/login" replace />;
  }
  ```
- `ProtectedRoute` с ролью (`useAuth()` → `user`, `isLoading`; нет user → `/login`; не та роль → `/unauthorized`).
- Защита через конфигурацию-массив маршрутов с флагами `requiredAuth` / `requiredRole`.
- **ProtectedLayout / PrivateOutlet** — обёртка с `<Outlet/>` для группы маршрутов: `<Route element={<PrivateOutlet/>}>…</Route>`; `AdminOutlet` для роли admin.
- **PublicRoute** — не пускать авторизованного на `/login` (редирект на `/dashboard`).
- Проверка в `useEffect` + `navigate('/forbidden')` возможна, но обёртки предпочтительнее (срабатывают до рендера контента).
- 404: `<Route path="*" element={<NotFound/>} />`.

### 12. HTTP-запросы: fetch и axios (лекция 14)

- Методы: GET (получить), POST (создать), PUT (заменить), PATCH (частично обновить), DELETE. Заголовки: `Content-Type`, `Authorization`, кэш.
- **fetch**: встроен, возвращает Promise; POST — `method`, `headers: {'Content-Type':'application/json'}`, `body: JSON.stringify(obj)`; **не отклоняет Promise на 4xx/5xx** — проверять `response.ok`; cookies только с `credentials: 'include'`; отмена — `AbortController`.
- **axios** (`npm install axios`): автопарсинг JSON (`response.data`, `.status`, `.headers`), отклоняет Promise на статусы ≥ 400, прогресс (`onUploadProgress`), `axios.create({ baseURL, timeout, headers })`, **interceptors**:
  ```js
  api.interceptors.request.use(cfg => {
    const t = localStorage.getItem('token');
    if (t) cfg.headers.Authorization = `Bearer ${t}`;
    return cfg;
  });
  api.interceptors.response.use(r => r, err => {
    if (err.response?.status === 401) { /* на /login */ }
    return Promise.reject(err);
  });
  ```
  Отмена — `CancelToken` (устар.) или `signal` от AbortController.
- Выбор: fetch — маленький проект без зависимостей; axios — interceptors, глобальная конфигурация, удобные ошибки. В production — отдельный модуль API (`apiClient`).

### 13. Состояния загрузки и ошибок (лекция 15)

- Три состояния: loading → success | error.
- `loading=true` перед каждым запросом, снятие в `finally`; скелетоны вместо спиннера; защита от мигания (показывать лоадер после ~200 мс).
- Ошибки axios: `err.response` (сервер ответил 4xx/5xx → switch по 401/403/404/500), `err.request` (нет ответа — сеть), иначе неизвестная. В fetch — `throw` по `response.status`.
- Кнопка «Повторить» → `refetch` (обёрнут в `useCallback`).
- Объединение состояния: `useState({data, loading, error})` или `useReducer` с действиями `FETCH_START` / `FETCH_SUCCESS` / `FETCH_ERROR`; кастомный `useFetch`.
- **Оптимистичное обновление** (сразу меняем UI, при ошибке — откат) vs **пессимистичное** (сначала ответ сервера — для критичных данных: финансы, бронирование).
- Обновление списков: добавление `[...prev, data]`, удаление `filter`, изменение `map`; пагинация «Загрузить ещё» — дописывать `[...prev, ...page]`.
- Refetch vs локальное обновление; серверное состояние — React Query (TanStack Query: `useQuery({queryKey, queryFn})`, `useMutation` + `invalidateQueries`), RTK Query, SWR.

### 14. Обновление интерфейса по данным сервера (лекция 16)

- Данные → `setState` → рендер. Замена (`setProducts(new)`) vs дописывание (`prev => [...prev, ...new]`).
- Оптимистичное добавление: временный id (`Date.now()`/`temp-…`) → POST → замена временного объекта на ответ сервера → при ошибке удалить + уведомление. Удаление: запомнить элемент → убрать → DELETE → при ошибке вернуть. Редактирование: запомнить старое → применить → PUT/PATCH → при ошибке откатить.
- Инвалидация/refetch после мутации (`fetchTodos` в `useCallback`).
- Реальное время: **polling** (`setInterval` 5 с) и **WebSocket** (`onmessage` → `setData(prev => ...)`, `ws.close()` в очистке).
- Связанные данные: ручное обновление нескольких состояний, `Promise.all` рефетч, либо кэш-библиотека.
- Оптимизация: `useMemo` (производные данные, сортировка), `useCallback` (колбэки детям), `React.memo`, дробление состояния.
- Полный пример CRUD-менеджера (`ProductManager`) с оптимистичными add/update/delete.

### 15. Prop drilling (лекция 17)

- Проброс данных через промежуточные компоненты, которым они не нужны (App → Header → Navbar → UserAvatar).
- Проблемы: загромождение, сложный рефакторинг, низкая переиспользуемость, трудная отладка, лишние перерендеры. Реальная проблема при > 3–4 уровнях и общих данных (тема, auth, локаль).
- Решения: **композиция** (передать готовый `<UserMenu user={user}/>` через `children` — «lifting content up»), **Context API**, глобальные сторы (Redux/Zustand/MobX), серверные кэши (React Query).

### 16. Context API (лекция 18)

- `createContext(default)` → `<Ctx.Provider value={...}>` → `useContext(Ctx)` (или устаревший `<Ctx.Consumer>`).
- Для: тема, язык, текущий пользователь, настройки, корзина. Не для: данных 2–3 соседних компонентов, очень частых обновлений (позиция мыши).
- Паттерн «провайдер + кастомный хук с проверкой»:
  ```jsx
  const AuthContext = createContext(null);
  export function AuthProvider({ children }) {
    const [user, setUser] = useState(null);
    const value = useMemo(() => ({ user, login: setUser, logout: () => setUser(null) }), [user]);
    return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
  }
  export const useAuth = () => {
    const c = useContext(AuthContext);
    if (!c) throw new Error('useAuth must be used within AuthProvider');
    return c;
  };
  ```
- Вложенные провайдеры переопределяют значение для поддерева; несколько контекстов в одном компоненте.
- Оптимизация: разделять контексты (стабильные/частые), мемоизировать `value` (`useMemo`), `use-context-selector`.
- Context vs Redux: встроен/отдельная библиотека; простота/сложность; все потребители перерендериваются / селекторы; базовые/мощные DevTools.
- Ошибки: нет Provider, новый объект в `value` каждый рендер, один контекст на всё, частые обновления.

### 17. useReducer (лекция 19)

- `const [state, dispatch] = useReducer(reducer, initialState, init?)`.
- Reducer — **чистая функция** `(state, action) => newState`: без мутаций, без побочных эффектов, `default: return state`.
- Action — объект `{ type: 'ADD_TODO', payload: {...} }` (type в UPPER_SNAKE_CASE; константы против опечаток).
- Когда вместо useState: объект с несколькими полями, сложные переходы, много разных действий, централизация логики, лёгкое тестирование.
- Ленивая инициализация: третий аргумент `init(initialArg)`.
- Пример todo-редьюсера: `ADD_TODO`, `TOGGLE_TODO`, `DELETE_TODO`, `SET_FILTER`.
- **Context + useReducer** = глобальное хранилище без Redux: `TodoProvider` отдаёт `{state, dispatch}`, хук `useTodo()`.

### 18. Комплексное управление состоянием (лекция 20)

- Спектр: локальный `useState` → поднятие состояния → композиция → Context → Context + useReducer → Redux Toolkit / Zustand / MobX.
- «Начинай с простого»; переходить на следующий уровень только при реальных симптомах.
- Три типа состояния: **локальное UI** (useState), **глобальное приложения** (Context + useReducer), **серверное** (React Query/SWR/RTK Query — не дублировать в контексте).
- Паттерн модуля состояния: константы действий → initialState → reducer → контекст → провайдер (`useMemo` для value) → хук `useCart()` → action creators (`addItem(item)`).
- Архитектура магазина: `ThemeProvider`, `AuthProvider`, `CartProvider`, `QueryClientProvider`, `Router` → Pages.
- Производительность: разделение `StateContext` и `DispatchContext`, `useMemo`, отдельные библиотеки для частых обновлений; отладка — обёртка-логгер `loggerReducer(reducer)`.
- Когда Redux/Zustand: сотни действий в секунду, сложная асинхронность (thunk/saga), громоздкий код, нужны time-travel DevTools.

## Как применить в проекте NotaCode

NotaCode — web-IDE «diagram-as-code» (текстовый DSL в стиле Mermaid/PlantUML → отрисованная диаграмма; проекты/файлы, аутентификация, шаринг). Фронтенд — **React + Vite + PWA**, бэкенд — **Python FastAPI**.

### ЛР5 → интеграция с сервером; вопрос о Node-сервере

**Что требует ЛР5.** Текст прямо говорит: приложение должно работать с *вашим собственным API из ЛР1–3 (Node.js + Express + PostgreSQL + JWT)*, запуск — `npm run dev` в `server/` и в `client/`. Разрешения заменить сервер на иной стек в материалах нет. Для самой клиентской части разрешено: axios или fetch, выбор улучшения (или своё, согласованное с преподавателем).

**Варианты для NotaCode (Python-бэкенд сохраняется):**

1. **Рекомендуемый — Node.js/Express BFF (API-gateway) перед FastAPI.** Сервер из ЛР1–3 (`server/`: Express + PostgreSQL + JWT) остаётся точкой входа фронтенда:
   - Express сам реализует `/api/auth/register`, `/api/auth/login` (JWT) и CRUD сущностей, требуемых ЛР1–3 (например, `/api/projects`, `/api/diagrams`), в PostgreSQL;
   - тяжёлые функции NotaCode (рендер DSL → SVG/PNG, валидация синтаксиса, экспорт) проксируются в FastAPI (`/api/render` → `http-proxy-middleware`/`axios` на `http://fastapi:8000`), FastAPI доверяет JWT, подписанному общим секретом;
   - React ходит только на `VITE_API_URL=http://localhost:3000/api` — формально условие ЛР5 выполнено полностью.
2. **Отдельный Node-микросервис для одной сущности** (например, только проекты/файлы + auth на Express/PostgreSQL), а рендер — прямые запросы к FastAPI. Сложнее с CORS и двумя базовыми URL; в `api.js` будет два экземпляра axios.
3. **Подключить React напрямую к FastAPI** — архитектурно проще, но это замена стека, не разрешённая материалами; допустимо только после согласования с преподавателем (аргумент: REST-контракт, JWT и CORS идентичны; `fastapi.middleware.cors.CORSMiddleware` вместо Express `cors`).

**Реализация клиентской части (одинакова для всех вариантов):**
- `.env`: `VITE_API_URL=http://localhost:3000/api`.
- `src/api.js`: `axios.create({ baseURL })`; request-interceptor с `Authorization: Bearer`; response-interceptor: 401 → очистка токена и `navigate('/login')`. Функции: `fetchDiagrams(projectId, {limit, offset, search, signal})`, `addDiagram`, `updateDiagram(id, patch)` (PATCH для частичного сохранения исходника), `deleteDiagram`, `renderDiagram(source, dsl)`.
- Компонент списка файлов: `loading` → скелетон дерева файлов, `error` → сообщение + «Повторить»; разбор `err.response.status` (401/403/404/500) vs `err.request` (сервер недоступен — скриншот для отчёта).
- Оптимистичные операции: создание файла с `temp-${Date.now()}` → замена на серверный id; удаление с возвратом при ошибке; переименование/сохранение с откатом.
- Доп. улучшение (выбрать одно; наиболее естественны для NotaCode):
  - **серверный поиск** по диаграммам (`GET /api/diagrams?search=` + debounce);
  - **AbortController** — отмена устаревшего запроса рендера предпросмотра при быстром наборе DSL (очень естественно для live-preview);
  - **retry** до 3 попыток для `/render`;
  - пагинация «Загрузить ещё» для списка проектов;
  - кэш ответов рендера в `localStorage` по хэшу исходника (+ хорошо сочетается с PWA).
- CORS: `app.use(cors({ origin: 'http://localhost:5173' }))` в Express (и `CORSMiddleware` в FastAPI, если к нему есть прямые запросы).

### ПЗ3 → маршрутизация NotaCode (React Router v6)

Соответствие обязательным маршрутам:

| Требуемый | В NotaCode |
|---|---|
| `/` главная | лендинг / быстрый старт |
| `/catalog` | `/projects` — список проектов пользователя (или галерея публичных примеров) |
| `/catalog/:id` | `/projects/:projectId` и `/projects/:projectId/files/:fileId` — редактор файла |

- `MainLayout` с `NavLink` (подсветка активного пункта, `end` у главной) и `<Outlet/>`.
- `PrivateOutlet` (`useAuth()` → `user` иначе `<Navigate to="/login" replace state={{from: location}}/>`); `PublicRoute` для `/login`; после входа `navigate(from ?? '/dashboard', {replace:true})`.

### ПЗ4 → Context + useReducer для состояния редактора

- **Prop drilling (часть 1):** показать исходную цепочку `App → EditorLayout → Toolbar → UserMenu → UserAvatar` с `userName`, затем устранить через `AuthContext`.
- **ThemeContext + LanguageContext** (обязательные): светлая/тёмная тема редактора и превью (также тема Mermaid `default`/`dark`), язык интерфейса RU/EN; `useMemo` для `value`.
- **EditorContext + editorReducer** — бизнес-логика NotaCode:
  ```js
  // state: { files: [], activeFileId, openTabs: [], dirty: {}, dsl: 'mermaid', history: [] }
  // actions: OPEN_FILE, CLOSE_TAB, UPDATE_SOURCE, SET_DSL, RENAME_FILE,
  //          ADD_FILE, REMOVE_FILE, MARK_SAVED, UNDO, RESET
  ```
  - «изменение количества» из критериев ↔ открытые вкладки / счётчик несохранённых файлов;
  - `UNDO` через массив истории (КВ24), `RESET` (КВ18), ленивая инициализация из `localStorage` (КВ20), разделение `EditorStateContext` и `EditorDispatchContext` (КВ27, КВ29), логгер-обёртка редьюсера для отладки (КВ19), тесты редьюсера как чистой функции в Vitest (КВ30).
- **AuthContext + authReducer** (`LOGIN_SUCCESS`, `LOGOUT`, `SET_LOADING`) — питает `PrivateOutlet` из ПЗ3 и interceptor из ЛР5.
- `localStorage`: сохранять открытые вкладки и черновики; восстанавливать при старте (часть 5).
- Разделение типов состояния по лекции 20: UI-локальное (открыт ли диалог шаринга) — `useState`; глобальное (тема, язык, auth, редактор) — Context + useReducer; серверное (списки проектов, результат рендера) — отдельный слой данных (кастомные хуки из ЛР5 или TanStack Query).

### Итоговая архитектура фронтенда NotaCode (удовлетворяет всем 4 работам)

```
main.jsx
└─ ThemeProvider → LanguageProvider → AuthProvider (useReducer) → EditorProvider (useReducer)
   └─ BrowserRouter
      └─ Routes
         ├─ MainLayout (NavLink + Outlet): /, /about, /share/:token, /login (PublicRoute)
         ├─ PrivateOutlet
         │   └─ /dashboard, /projects, /projects/:projectId/files/:fileId (lazy Editor)
         └─ * → NotFound
src/api.js  — axios instance (VITE_API_URL → Express BFF :3000/api → FastAPI), interceptors
src/hooks/  — useLocalStorage, useDebounce, useFetch/useDiagrams (loading/error/AbortController)
```

- Ветки сдачи: `24` (ЛР4 — локальный список + localStorage), `25` (ЛР5 — api.js + BFF), `pz23` (маршруты), `pz24` (контексты). Основная разработка ведётся в `main`, а для каждой работы делать ветку-срез с нужной функциональностью.

### Применение теории к фичам NotaCode (кратко)

- JSX-экранирование и `dangerouslySetInnerHTML`: SVG от рендерера вставлять только после санитизации (DOMPurify) — это недоверенный контент из пользовательского DSL.
- `useEffect` + debounce + AbortController — live-preview диаграммы при наборе.
- `key` по стабильному `file.id` в дереве файлов и вкладках.
- MUI/Chakra (опционально) — AppBar, Drawer дерева файлов, Modal «Поделиться», Switch темы; тема MUI синхронизируется с `ThemeContext`.
- Оптимистичное/пессимистичное обновление: переименование/удаление — оптимистично; генерация ссылки шаринга и удаление проекта — пессимистично.
