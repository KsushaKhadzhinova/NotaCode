## 1. Что такое КР и какие у неё обязательные требования

**Суть:** самостоятельно разработать полнофункциональное веб-приложение. Обязательные составляющие по Рекомендациям и учебной программе, п. 2.5:

| Требование | Как сформулировано в материалах |
|---|---|
| Клиентская часть | **React** (SPA) |
| Серверная часть | **Node.js / Express** |
| База данных | **PostgreSQL или MongoDB** |
| Аутентификация | обязательна; в структуре ПЗ это JWT и bcrypt |
| Функциональность | **не менее 3** основных функциональных модулей |
| Объём ПЗ | Рекомендации: 25–30 с.; «Структура»: 20–30 с. без приложений |
| Трудоёмкость | 30 академических часов, 1 з. е. |
| Цель | закрепить клиентскую и серверную разработку, проектирование и развёртывание |

По структуре ПЗ ожидается ещё следующее (эти пункты описываются в главе 2):
- REST API с валидацией и обработкой ошибок;
- helmet, cors, bcrypt;
- React Router с защищёнными маршрутами, Context или useReducer, axios или fetch с состояниями загрузки и ошибок, адаптивная вёрстка;
- Dockerfile и docker-compose;
- деплой в облако;
- тесты: Jest для API или ручные сценарии;
- CI/CD и мониторинг ошибок желательны (приложение Г).

## 2. Выбор темы

- Список «Темы КП» содержит 150 тем. Номер темы выдаёт **Генератор вариантов тем**. Он детерминированный: номер вычисляется по хешу FNV-1a от параметров студента (год поступления, группа, номер в журнале, форма обучения).
  - Очная форма: 1-я группа получает темы 1–30, 2-я — 31–60, 3-я — 61–90, 4-я — 91–120.
  - Дистанционная форма: темы 121–150.
  - Внутри группы из 30 студентов все номера разные.
- В учебной программе, п. 2.5, есть отдельный базовый список из 10 тем: TODO-приложение, блог, интернет-магазин, бронирование, онлайн-курсы, личные финансы, соцсеть, мероприятия, CMS, совместная работа над документами.
- Лабораторные ЛР1–ЛР8 части 2 прямо требуют строить всё вокруг «предметной области вашего курсового проекта». Лабораторные — это поэтапная сборка КР.
- Темы, близкие к NotaCode:
  - 125 «обучение программированию с выполнением кода в браузере (IDE)»;
  - 114 «визуализация алгоритмов»;
  - 17 и 150 «совместная работа над документами» (150 — в реальном времени);
  - 47 «заметки с Markdown и тегами»;
  - 84 «Wiki с версионированием».

  Тема NotaCode (diagram-as-code IDE) должна либо совпасть с выданным номером по смыслу, либо **быть согласована с преподавателем** как собственная.

## 3. Структура пояснительной записки (по файлу «Структура…»)

Порядок элементов и рекомендуемый объём:

1. **Титульный лист** по Стандарту предприятия (образец в СТП, приложение В; для КР берётся шаблон кафедры).
2. **Задание на курсовую работу** по шаблону.
3. **Содержание**, автоматически собранное в Word.
4. **Перечень условных обозначений, сокращений и терминов** — необязателен, до 1 с. Примеры: API, SPA, JSX, REST, JWT, ORM, CI/CD, «деплой».
5. **Введение** (1–1,5 с.):
   - актуальность;
   - цель: «Разработать полнофункциональное веб-приложение „[Название]“ на современном стеке»;
   - задачи:
     1. проанализировать предметную область и требования;
     2. спроектировать архитектуру и выбрать стек;
     3. реализовать сервер (REST API, БД, аутентификация);
     4. сделать клиент (React SPA, адаптивный);
     5. интегрировать, протестировать, развернуть;
   - объект — процесс разработки веб-приложений; предмет — методы и технологии создания SPA на React, Node.js и PostgreSQL/MongoDB;
   - практическая значимость;
   - абзац о структуре работы.
6. **Глава 1. Анализ и проектирование системы** (7–8 с.):
   - 1.1 Анализ предметной области и требования (2 с.): проблема; функциональные требования (FR) в виде пользовательских историй «Пользователь может…»; нефункциональные (NFR): производительность, безопасность, адаптивность.
   - 1.2 Архитектура (3 с.):
     - логическая: Use Case диаграмма для акторов «Пользователь» и «Администратор»;
     - физическая: схема «Клиент – Сервер – БД» с технологиями (React, Express, Nginx, PostgreSQL), вместо неё допустима C4 уровня 1 (контекстная);
     - таблица REST-эндпоинтов: метод, URL, описание, пример тела запроса и ответа.
   - 1.3 Структура данных (2 с.): ER-диаграмма на 4–6 сущностей с ключевыми атрибутами и связями, краткое описание таблиц или коллекций.
7. **Глава 2. Реализация** (12–13 с.):
   - 2.1 Выбор и обоснование стека (1,5 с.), с таблицей сравнения:
     - React — компонентный подход, Virtual DOM, экосистема;
     - Node.js + Express — асинхронность, единый язык, скорость разработки;
     - PostgreSQL (надёжность, транзакции) или MongoDB (гибкая схема);
     - Git, Docker, Postman, VS Code.
   - 2.2 Backend (4 с.):
     - 2.2.1 структура проекта (models, routes, controllers, middleware) и package.json;
     - 2.2.2 ключевая модель на Sequelize или Mongoose с комментариями;
     - 2.2.3 контроллер CRUD с валидацией;
     - 2.2.4 схема JWT, middleware проверки токена, защищённый маршрут;
     - 2.2.5 ошибки и безопасность: helmet, cors, валидация, bcrypt.
   - 2.3 Frontend (4 с.):
     - 2.3.1 структура (src/components, src/pages, src/context);
     - 2.3.2 React Router: публичные и защищённые маршруты;
     - 2.3.3 компонент с useState/useEffect, глобальное состояние (Context или useReducer);
     - 2.3.4 fetch или axios, состояния загрузки и ошибок;
     - 2.3.5 адаптивность: CSS-модули или Styled Components, Flexbox/Grid.
   - 2.4 Интеграция, сборка, развёртывание (2,5 с.):
     - 2.4.1 прокси в dev-режиме, CORS;
     - 2.4.2 Dockerfile для backend (frontend — опционально) и docker-compose.yml для всего стека;
     - 2.4.3 деплой (пример: Render для backend и БД, Netlify для frontend);
     - 2.4.4 тестирование: модульные тесты Jest для API или ручные сценарии.
8. **Глава 3. Руководство пользователя и тестирование** (4–5 с.):
   - 3.1 Руководство пользователя (2,5 с.):
     - требования к браузеру;
     - запуск для разработчика: `git clone`, `npm i`, `docker-compose up`;
     - пошаговое описание 2–3 сценариев (например, регистрация, создание сущности);
     - 3–4 скриншота: главная, вход, панель управления.
   - 3.2 Контрольные примеры (1,5 с.): таблица «Исходные данные → Действия → Ожидаемый результат → Фактический (Пройдено/Не пройдено)» и вывод о соответствии требованиям.
9. **Заключение** (1 с.): решённые задачи, констатация «цель достигнута», URL развёрнутого приложения и список функций, перспективы (push-уведомления, мобильное приложение, аналитика).
10. **Список использованных источников** (1 с.): **15–20 источников** по ГОСТ или Стандарту предприятия. Что туда брать:
    - официальную документацию React, Node, Express;
    - учебники из учебной программы;
    - книги не старше 5 лет;
    - статьи Habr, MDN, Stack Overflow за 2022–2026 годы;
    - репозитории GitHub.
11. **Приложения** (в объём 25–30 с. не входят):
    - А — полный листинг кода (если требуется);
    - Б — исходные данные для тестирования;
    - В — полные скриншоты всех экранов;
    - Г — рекомендации по бесплатным сервисам (см. п. 6).

## 4. Оформление по СТП 01–2024

Разделы 2 и 3 СТП распространяются на курсовые работы и отчёты по лабораторным.

- **Страница:** А4, текст на одной стороне. Поля: левое 30 мм, правое 15 мм, верхнее и нижнее 20 мм.
- **Шрифт:** Times New Roman 14 пт, межстрочный интервал 1,0 (18 пт), абзацный отступ 1,25 см, выравнивание по ширине. Автоматические переносы в тексте разрешены, в заголовках, названиях таблиц и рисунков запрещены.
- **Заголовки:**
  - разделы нумеруются арабскими цифрами без точки и пишутся прописными; подразделы (1.1) — строчными с заглавной буквы;
  - полужирные, с абзацного отступа, выравнивание влево, без точки в конце, без подчёркивания;
  - между заголовком и текстом — одна пустая строка;
  - каждый раздел рекомендуется начинать с новой страницы;
  - ненумерованные заголовки (СОДЕРЖАНИЕ, ВВЕДЕНИЕ, ЗАКЛЮЧЕНИЕ, СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ, ПРИЛОЖЕНИЕ) — по центру, без отступа;
  - многострочный заголовок выравнивается по первой букве первой строки;
  - если текст после заголовка подраздела не помещается на странице, заголовок переносится на следующую.
- **Содержание:** слово СОДЕРЖАНИЕ полужирное, 14–16 пт, по центру. Уровни сдвигаются на 2 знака, заголовок соединяется с номером страницы отточием.
- **Нумерация страниц:** арабские цифры в правом нижнем углу. Титульный лист, задание и реферат входят в нумерацию, но номер на них не ставится. Приложения входят в общую нумерацию.
- **Перечисления:**
  - простое — каждый элемент с новой строки с «–», в конце «;»;
  - сложное — элементы нумеруются «1 …» и заканчиваются точкой;
  - для ссылок на элементы используются «а)», «б)», для вложенных уровней «1)»;
  - вводная фраза не обрывается на предлоге (не «состоит из:»).
- **Числа:**
  - от одного до девяти без единиц измерения пишутся словами;
  - диапазон — «от 2 до 20 км»;
  - «не более / не менее»;
  - единицы — по ГОСТ 8.417–2002;
  - знаки (<, >, =, %, №) без чисел пишутся словами.
- **Формулы:**
  - номер в круглых скобках у правого края;
  - ссылка вида «формула (3.6)»;
  - пояснения начинаются со слова «где» без двоеточия, с новой строки без отступа, каждое заканчивается «;».
- **Рисунки:**
  - по центру, отделяются пустой строкой;
  - подпись «Рисунок 2.7 – Название», без точки в конце; в приложении — «Рисунок А.2»;
  - на каждый рисунок в тексте нужна ссылка («на рисунке 2.1…»);
  - рисунок должен читаться без поворота или с поворотом на 90° по часовой стрелке.
- **Таблицы:**
  - над таблицей слева «Таблица 2.1 – Заголовок» (слово не сокращается); в приложении — «Таблица Б.2»;
  - перенос оформляется как «Продолжение таблицы 2.1», можно с нумерацией граф;
  - графа «№ п/п» не допускается;
  - пустые ячейки не допускаются (ставится тире);
  - заголовки граф пишутся с прописной буквы.
- **Приложения:**
  - на каждое нужна ссылка в тексте, порядок — по ссылкам;
  - обозначаются буквами А, Б, В… (кроме Ё, З, Й, О, Ч, Ъ, Ы, Ь);
  - каждое начинается с новой страницы: «ПРИЛОЖЕНИЕ А», ниже «(обязательное / рекомендуемое / справочное)», ниже заголовок.
- **Источники:**
  - ссылки в тексте в квадратных скобках [6], нумерация по порядку первого упоминания;
  - список «СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ» с новой страницы по центру, перед приложениями;
  - описания по ГОСТ 7.1–2003, пример для сайта: `Xilinx [Электронный ресурс]. – Режим доступа : http://…`;
  - знаки «: ; – /» отбиваются пробелами, «Минск» пишется полностью;
  - лекционные материалы можно использовать без ссылок, но в конце списка их нужно перечислить.
- **Сноски и примечания:** сноска — цифра со скобкой. «Примечание – …» для одного примечания, нумерованный список для нескольких.
- **Схемы алгоритмов, программ, данных и систем:** СТП, п. 3.12, по ЕСКД/ЕСПД (ГОСТ 19.701). Это важно для блок-схем. Диаграммы — п. 3.11.
- Оформление отчётов по ЛР тоже следует СТП (см. `00-general.md`).

## 5. Сроки и оценивание

- **Когда:** 7-й семестр (4 курс) на дневной форме, итог — «Экзамен, курсовая работа»; на дистанционной — 9-й семестр. Конкретных календарных дат (опроцентовок, крайнего срока сдачи ПЗ, даты защиты) **в материалах нет**. Их нужно уточнить у преподавателя или в СЭО.
- **Как оценивается:** критериев оценки КР **в материалах нет**. Действует общая 10-балльная шкала БГУИР. Учебная программа, п. 2.9, упоминает «рубричное оценивание работ».
- **Логично ожидаемые критерии** (выведены из структуры, в материалах их нет): все обязательные компоненты стека, не менее 3 модулей, аутентификация, развёрнутое приложение по URL, ПЗ по СТП, защита с демонстрацией.
- **Сдача:** по общим правилам курса — репозиторий GitHub с README и инструкцией запуска плюс PDF в СЭО. Выдержка из файла «ПО и инструкции»: «Все задания сдаются в виде ссылок на репозиторий GitHub».

## 7. Как применить в проекте NotaCode

**Конфликт стека.** Формально КР требует «серверную часть (Node.js/Express)», а в 2.1 и 2.2 ПЗ описываются Express и Sequelize/Mongoose. Основной backend NotaCode написан на Python FastAPI. Официального разрешения заменить Node на Python в материалах КР **нет**. При этом учебная программа (раздел 4, тема 21) включает FastAPI в курс, а Python в ней указан среди технологий серверной разработки. Варианты, от безопасного к рискованному:

1. **Рекомендуется: Node BFF / API-gateway + FastAPI как сервис рендеринга.**
   - `gateway/` на Node.js + Express + Sequelize (PostgreSQL) отвечает за пользователей, регистрацию и вход (bcrypt + JWT), проекты, файлы диаграмм, шаринг, права (роли owner/editor/viewer), helmet, cors, валидацию (express-validator или zod) и Swagger.
   - FastAPI (`renderer/`) остаётся внутренним сервисом: парсинг и валидация DSL, рендер в SVG/PNG (Mermaid, PlantUML, Graphviz), экспорт, тяжёлые вычисления. Gateway проксирует `/api/render/*` в FastAPI.
   - Так формально выполнено «Node.js/Express + Sequelize + JWT» (ЛР1–ЛР3 и ЛР5 ложатся без натяжек), а Python остаётся ядром. В ПЗ это описывается как микросервисная архитектура (связь с темой 32 «Монолит vs микросервисы» и SOA из модуля 05).
2. **Замена по согласованию.** Весь backend на FastAPI, а в 2.1 ПЗ — сравнительная таблица Node.js/Express против FastAPI (материал модуля 03, лекция 01) с обоснованием: типизация Pydantic, автогенерация OpenAPI, async, экосистема для рендеринга. Требует **письменного или устного согласия преподавателя**, иначе есть риск незачёта требования «Node.js/Express».
3. **Гибрид для ЛР6/ЛР7.** Отдельные Node-сервисы: `realtime/` на Socket.IO (совместное редактирование) и, при необходимости, Mongo-сервис для истории ревизий — см. `03-alternative-tech.md`.

**Сопоставление требований КР с NotaCode:**

| Требование КР | Реализация в NotaCode |
|---|---|
| React SPA | React + Vite + PWA: редактор (CodeMirror/Monaco) с живым превью |
| Node.js/Express | gateway (вариант 1) |
| PostgreSQL/MongoDB | PostgreSQL (users, projects, diagrams, diagram_versions, shares, templates); MongoDB — опционально для ревизий |
| Аутентификация | JWT access + refresh, bcrypt, защищённые маршруты `/app/*` |

**Подсказки по ПЗ:**
- Все диаграммы ПЗ (Use Case, C4, ER, схемы алгоритмов) можно **сгенерировать самим NotaCode**. Это хорошая демонстрация практической значимости, но оформление должно соответствовать СТП п. 3.11–3.12 и ГОСТ 19.701.
- В 3.2 нужно 8–12 контрольных примеров: регистрация, вход с неверным паролем, создание диаграммы, синтаксическая ошибка DSL (сообщение с номером строки), экспорт SVG, шаринг по ссылке, доступ без прав (403), офлайн-правка с последующей синхронизацией.
- Код ЛР хранится в том же репозитории в ветках, которые требуют лабораторные (`lab21`, `lab12`/`22`, `23`, `24`–`28`, `pz21`–`pz24`), а КР собирать в `main`.
