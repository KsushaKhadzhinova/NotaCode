## 1. Designing Data-Intensive Applications — Мартин Клеппман

**Библиография**
- Martin Kleppmann. *Designing Data-Intensive Applications: The Big Ideas Behind Reliable, Scalable, and Maintainable Systems*. O'Reilly, 2017. ISBN 978-1449373320.
- 2-е изд.: Martin Kleppmann, Chris Riccomini. O'Reilly, 2026. ISBN 978-1098119065.
- Рус. изд. (1-е): Мартин Клеппман. *Высоконагруженные приложения. Программирование, масштабирование, поддержка*. СПб.: Питер, 2018.

**Ключевые принципы**
1. **Надёжность, масштабируемость, сопровождаемость** — три цели; нагрузка описывается параметрами, производительность — перцентилями (p50/p95/p99), а не средним.
2. **Модели данных:** реляционная, документная, графовая; выбор по форме связей (документ — для деревьев «один-ко-многим»).
3. **Движки хранения:** LSM-деревья против B-деревьев; OLTP против OLAP; колоночное хранение.
4. **Кодирование и эволюция схем:** прямая и обратная совместимость; Avro/Protobuf/JSON Schema.
5. **Репликация:** single-leader, multi-leader, leaderless; задержка репликации и гарантии read-your-writes, monotonic reads, consistent prefix.
6. **Шардирование:** по диапазону ключа или хэшу; горячие точки; перебалансировка.
7. **Транзакции:** ACID, уровни изоляции (read committed, snapshot isolation, serializable), аномалии (lost update, write skew, phantom).
8. **Проблемы распределённых систем:** ненадёжная сеть, ненадёжные часы, паузы процессов; нельзя отличить медленный узел от мёртвого.
9. **Согласованность и консенсус:** линеаризуемость, причинность, total order broadcast; цена линеаризуемости (CAP в корректной формулировке).
10. **Пакетная и потоковая обработка:** неизменяемые логи событий, CDC, event sourcing.
11. **Точно-один-раз = как-минимум-один-раз + идемпотентность.**
12. **Конфликты при одновременной записи:** LWW теряет данные; альтернативы — версионные векторы, слияние на уровне приложения, CRDT.
13. **Сквозная корректность (end-to-end argument):** идентификатор запроса, проходящий от клиента до БД, для дедупликации.
14. **Разделение системы записи (system of record) и производных данных** (кэши, индексы, представления).

**Применение в NotaCode**
- **Система записи** — PostgreSQL (`diagrams`, `diagram_versions`, `outbox_events`). Производные данные — превью-картинки, кэш компиляции, поисковый индекс — всегда перестраиваемы из версий.
- **Конкурентные правки:** snapshot isolation (REPEATABLE READ) + optimistic lock по `revision`; при конфликте — трёхстороннее слияние DSL-текста (base = общий предок-версия) на клиенте, а не LWW.
- **Совместное редактирование в реальном времени (фаза 2):** CRDT (Yjs) для текста DSL; сервер хранит снапшоты как обычные версии.
- **Идемпотентность записей:** каждый мутирующий запрос несёт `Idempotency-Key` (UUID, генерирует клиент); сервер хранит `(user_id, key) → response` 24 ч. Офлайн-очередь PWA при повторной отправке не создаёт дублей версий.
- **Версионирование схемы модели:** поле `schema_version` в JSONB-модели; миграторы `vN → vN+1` — чистые функции с тестами; чтение старых версий всегда возможно (обратная совместимость навсегда для истории).
- **Метрики задержки** — только перцентили (p95/p99) в дашбордах и SLO.
- **Контент-адресация версий:** `content_hash = sha256(canonical_source)` — дедупликация одинаковых сохранений и быстрый «нет изменений».

## 2. Building Microservices, 2nd Edition — Сэм Ньюмен

**Библиография**
- Sam Newman. *Building Microservices: Designing Fine-Grained Systems*. 2nd ed. O'Reilly, 2021. ISBN 978-1492034025. (1-е изд. — 2015.)
- Рус. изд.: Сэм Ньюмен. *Создание микросервисов*. 2-е изд. СПб.: Питер, 2023 (1-е изд. — 2016).
- Также: S. Newman. *Monolith to Microservices*. O'Reilly, 2019 (рус.: *От монолита к микросервисам*, БХВ, 2021).

**Ключевые принципы**
1. **Микросервис — независимо развёртываемый сервис, смоделированный вокруг бизнес-домена;** независимая развёртываемость — главное свойство.
2. **Сокрытие информации:** сервис владеет своими данными; общая БД — антипаттерн.
3. **Границы по DDD:** агрегаты и ограниченные контексты.
4. **Типы связанности** (от слабой к сильной): доменная, сквозная (pass-through), общая, по содержимому.
5. **Стили коммуникации:** синхронный запрос-ответ, асинхронный, событийный, через общие данные.
6. **Оркестрация против хореографии** в сагах; хореография снижает связанность, но усложняет наблюдаемость.
7. **Миграция — постепенно:** Strangler Fig, Branch by Abstraction, Parallel Run, декомпозиция БД.
8. **Сборка и развёртывание:** один сервис — один репозиторий или монорепо с независимыми пайплайнами; контейнеры; прогрессивная доставка (canary, feature toggles).
9. **Тестирование:** контрактные тесты (consumer-driven) вместо хрупких сквозных e2e.
10. **Наблюдаемость:** агрегированные логи, распределённая трассировка, correlation ID.
11. **Безопасность:** zero trust, mTLS между сервисами, принцип наименьших привилегий, JWT для передачи контекста.
12. **Устойчивость:** таймауты, ретраи, bulkheads, circuit breakers, идемпотентность.
13. **Закон Конвея** — структура команд и архитектура взаимосвязаны.
14. **Микросервисы — не цель;** сначала спросите, какую проблему решаете.

**Применение в NotaCode**
- **Сейчас — модульный монолит;** при выделении сервиса используем **Strangler Fig**: новый сервис встаёт за тем же API-шлюзом (Traefik/NGINX), маршрут переключается фичефлагом.
- **Никаких общих таблиц между выделенными сервисами:** `export-worker` получает задание через очередь (`ExportRequested` с полной моделью/ссылкой на версию) и возвращает результат событием; к таблицам API он не ходит.
- **Correlation ID:** заголовок `traceparent` (W3C Trace Context) + `X-Request-ID`, пробрасывается в логи, события outbox и задания воркеров.
- **Контрактные тесты** фронт ↔ API по OpenAPI (schemathesis + сгенерированный TS-клиент — сборка падает при расхождении).
- **Feature toggles** (OpenFeature-совместимый провайдер) для постепенного включения нотаций и AI-ассистента.

## 3. Microservices Patterns — Крис Ричардсон

**Библиография**
- Chris Richardson. *Microservices Patterns: With Examples in Java*. Manning, 2018. ISBN 978-1617294549. (2-е изд. — в работе, Manning MEAP.)
- Каталог паттернов: https://microservices.io/patterns/
- Рус. изд.: Крис Ричардсон. *Микросервисы. Паттерны разработки и рефакторинга*. СПб.: Питер, 2019.

**Ключевые принципы**
1. **Декомпозиция** по бизнес-возможностям или по субдоменам.
2. **Database per Service** и следствие — отсутствие распределённых ACID-транзакций.
3. **Сага** — последовательность локальных транзакций с компенсирующими действиями; хореографическая или оркестрационная.
4. **Countermeasures** для отсутствия изоляции в сагах: семантическая блокировка, коммутативные обновления, пессимистичное представление, перечитывание значения, файл версий.
5. **Transactional Outbox** + **Polling Publisher** или **Transaction Log Tailing (CDC)** — надёжная публикация событий.
6. **Idempotent Consumer** — дедупликация по ID сообщения.
7. **API Gateway** и **Backends for Frontends (BFF).**
8. **API Composition** и **CQRS** для запросов через несколько сервисов.
9. **Event Sourcing** как способ атомарно менять состояние и публиковать события.
10. **Service Discovery** (клиентский/серверный), **Circuit Breaker**.
11. **Наблюдаемость:** Health Check API, Log Aggregation, Distributed Tracing, Application Metrics, Exception Tracking, Audit Logging.
12. **Тестирование:** consumer-driven contract, component tests, пирамида.
13. **Развёртывание:** контейнеры, serverless, service mesh; **Externalized Configuration**.
14. **Strangler Application** для миграции монолита.

**Применение в NotaCode**
- **Transactional Outbox + Polling Publisher** (решение по умолчанию, без Debezium на старте):
  ```
  BEGIN;
    INSERT INTO diagram_versions ...;
    UPDATE diagrams SET head_version_id = ..., revision = revision + 1 WHERE id = ... AND revision = :expected;
    INSERT INTO outbox_events (event_id, type, aggregate_id, payload, created_at) ...;
  COMMIT;
  ```
  Релэй: `SELECT ... FROM outbox_events WHERE published_at IS NULL ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED` → публикация → `published_at = now()`. Очистка опубликованных старше 7 дней.
- **Idempotent Consumer:** таблица `processed_messages(consumer, event_id)` с уникальным индексом; обработка и отметка — в одной транзакции.
- **Оркестрационная сага** для синхронизации с GitHub (`SyncSaga`: создать ветку/коммит → обновить ссылку → записать `sync_links`; компенсация — пометить `sync_status=conflict`, уведомить пользователя).
- **Health Check API:** `/health/live` (процесс жив) и `/health/ready` (БД, Redis доступны) — для Docker/Kubernetes probes.
- **Exception Tracking** → GlitchTip (Sentry-совместимый SDK).
- **BFF не нужен** на старте (один клиент); появится при мобильном/VS Code-клиенте.
- **Audit Logging:** журнал действий (кто, что, когда) — отдельная append-only таблица `audit_log`.

## 4. Designing Distributed Systems — Брендан Бёрнс

**Библиография**
- Brendan Burns. *Designing Distributed Systems: Patterns and Paradigms for Scalable, Reliable Services*. O'Reilly, 2018. ISBN 978-1491983645. (2-е изд. — O'Reilly, 2024.)
- Рус. изд. (1-е): Брендан Бёрнс. *Распределённые системы. Паттерны проектирования*. СПб.: Питер, 2019.

**Ключевые принципы**
1. **Контейнеры как строительные блоки,** паттерны — как повторно используемые компоненты.
2. **Одноузловые паттерны:** Sidecar (дополнение основного контейнера), Ambassador (прокси к внешнему миру), Adapter (унификация интерфейса, например метрик).
3. **Паттерны обслуживания:** реплицированные сервисы без состояния за балансировщиком, шардированные сервисы, scatter/gather.
4. **Готовность (readiness) против живучести (liveness).**
5. **Кэширующий слой** перед сервисом; сессионная привязка при необходимости.
6. **Шардирование с консистентным хэшированием.**
7. **FaaS / событийная обработка** для редких или неравномерных нагрузок.
8. **Выборы лидера** и блокировки через распределённое KV-хранилище (etcd) с TTL.
9. **Пакетная обработка:** work queue, event-driven batch, copier, filter, splitter, sharder, merger, join/barrier.
10. **Координированная пакетная обработка:** MapReduce-подобные конвейеры.
11. **Идемпотентные воркеры** в очередях работ.
12. (2-е изд.) — паттерны для AI-нагрузок, наблюдаемость, типичные ошибки.

**Применение в NotaCode**
- **Stateless API-реплики** за балансировщиком; всё состояние — в PostgreSQL/Redis; сессии не хранятся в памяти процесса (JWT + refresh в БД).
- **Work Queue** для экспорта PNG/PDF и тяжёлых раскладок: Redis Streams (consumer groups) → `export-worker` (N реплик), с ACK, повторной доставкой и DLQ (`exports:dead`) после 5 попыток.
- **Sidecar:** OpenTelemetry Collector как sidecar/agent; **Adapter** — экспорт метрик в формате Prometheus.
- **Ambassador:** доступ к LLM-провайдерам через `ai-gateway` (ретраи, rate limit, учёт токенов) — основной код знает только порт.
- **Выбор лидера** для единственного экземпляра релэя outbox не требуется благодаря `SKIP LOCKED` (конкурентные релэи безопасны).

## 5. Designing Event-Driven Systems — Бен Стопфорд

**Библиография**
- Ben Stopford. *Designing Event-Driven Systems: Concepts and Patterns for Streaming Services with Apache Kafka*. O'Reilly/Confluent, 2018. ISBN 978-1492038221. Бесплатный e-book от Confluent.
- Рус. изд.: нет.

**Ключевые принципы**
1. **События как общий источник истины** — лог событий заменяет общую БД как точку интеграции.
2. **Три роли событий:** уведомление, перенос состояния (event-carried state transfer), источник данных (event sourcing).
3. **Команды, события, запросы** — разные виды взаимодействия с разной связанностью.
4. **Kafka как распределённый лог:** партиции, упорядочивание внутри ключа, хранение, compacted topics.
5. **Дихотомия данных:** сервисы инкапсулируют данные, но данные должны быть разделяемыми — лог решает этот конфликт.
6. **Event Sourcing, CQRS, материализованные представления** на потоке.
7. **Exactly-once в Kafka** через идемпотентных продюсеров и транзакции.
8. **Схемы событий и их эволюция** (Schema Registry).
9. **Stateful stream processing** (Kafka Streams): join, window, таблицы из потоков.
10. **Согласованность и параллелизм:** ключ партиционирования определяет порядок; «один писатель» на сущность.
11. **Хореография потоками** вместо синхронных цепочек вызовов.
12. **Оперативные представления («view») локальны сервису** и перестраиваются из лога.

**Применение в NotaCode**
- **Ключ партиционирования/стрима = `diagram_id`**, чтобы события одной диаграммы обрабатывались по порядку.
- **Event-carried state transfer** для `VersionCommitted` → payload содержит `diagram_id`, `version_id`, `notation`, `content_hash`, `source_ref` (ссылка, не полный исходник > 64 КБ).
- **Схемы событий** описаны Pydantic-моделями и экспортируются в JSON Schema (`docs/architecture/events/*.schema.json`); изменения только аддитивные, версия в поле `type` (`diagram.version_committed.v1`).
- **Брокер:** на старте Redis Streams; путь миграции на Kafka/Redpanda сохранён за портом `EventPublisher`.
- **Принцип «один писатель»:** только контекст Versioning пишет события версии.

## 6. Release It!, 2nd Edition — Майкл Найгард

**Библиография**
- Michael T. Nygard. *Release It! Design and Deploy Production-Ready Software*. 2nd ed. Pragmatic Bookshelf, 2018. ISBN 978-1680502398. (1-е изд. — 2007.)
- Рус. изд. (1-е изд.): Майкл Нейгард. *Release it! Проектирование и дизайн ПО для тех, кому не всё равно*. СПб.: Питер, 2016. Перевода 2-го изд. нет.

**Ключевые принципы**
1. **Продакшен — единственное место, где проверяется система;** проектируйте под эксплуатацию.
2. **Антипаттерны стабильности:** точки интеграции, цепные реакции, каскадные отказы, пользователи (нагрузка), блокированные потоки, самовызванный DDoS, неограниченные наборы результатов, медленные ответы, SLA-инверсия, нехватка масштаба.
3. **Timeouts** — на каждом сетевом вызове.
4. **Circuit Breaker** — после серии отказов перестать звать зависимость, периодически пробовать (closed → open → half-open).
5. **Bulkheads** — изоляция пулов ресурсов, чтобы отказ одной части не топил всё судно.
6. **Steady State** — система сама чистит за собой (логи, данные, кэши).
7. **Fail Fast** — отказывать сразу, если ясно, что запрос не выполнить.
8. **Let It Crash**, **Handshaking**, **Back Pressure**, **Load Shedding**, **Governor** (ограничитель скорости автоматических действий).
9. **Test Harness** — имитация нестандартных отказов внешних систем.
10. **Decoupling Middleware** — асинхронность снижает связанность по времени.
11. **Прозрачность:** логи, метрики, health checks, трассировки — встроены.
12. **Развёртывание без простоев:** миграции схем в несколько шагов (expand/contract), blue-green, canary.
13. **Хаос-инжиниринг** как проверка устойчивости.

Цитата: «Every integration point will eventually fail in some way» (М. Найгард).

**Применение в NotaCode**
- **Таймауты везде:** HTTP-клиент `httpx` с `timeout=Timeout(connect=2, read=10)` к GitHub/Drive/LLM; SQL `statement_timeout = 5s` для API-пула, 60s для воркеров; фронт — `AbortController` 15 с.
- **Circuit breaker** на каждую внешнюю интеграцию (GitHub, Google Drive, LLM, рендер): 5 ошибок за 30 с → open на 60 с → half-open одним пробным запросом; в open — мгновенный `503` с `Retry-After` и понятным UI («GitHub недоступен, версия сохранена в NotaCode»).
- **Ретраи:** только для идемпотентных операций, экспоненциальная задержка с полным джиттером (base 200 мс, cap 10 с, max 5 попыток); `tenacity` в Python.
- **Bulkheads:** раздельные пулы соединений БД для API и воркеров; раздельные очереди/воркеры для экспорта и синхронизации; ограничение параллелизма `asyncio.Semaphore` на внешние вызовы.
- **Неограниченные результаты запрещены:** все списки — с пагинацией (keyset/cursor, `limit ≤ 100`); ограничения размера: исходник DSL ≤ 1 МБ, ≤ 5 000 элементов на диаграмму, тело запроса ≤ 2 МБ.
- **Load shedding / back pressure:** при длине очереди экспорта > порога — `429`/`503` с `Retry-After`.
- **Steady state:** TTL на `idempotency_keys`, очистка outbox, ротация логов, лимит версий автосохранений (сжатие черновиков старше 30 дней до ежедневных).
- **Expand/contract миграции** Alembic: добавить колонку → двойная запись → бэкфилл → переключить чтение → удалить старое, каждое — отдельный релиз.

## 7. Web Scalability for Startup Engineers — Артур Эйсмонт

**Библиография**
- Artur Ejsmont. *Web Scalability for Startup Engineers: Tips & Techniques for Scaling Your Web Application*. McGraw-Hill Education, 2015. ISBN 978-0071843652.
- Рус. изд.: нет.

**Ключевые принципы**
1. **Масштабирование вертикальное и горизонтальное;** функциональное разбиение, шардирование.
2. **Фронтенд-слой без состояния:** сессии вне веб-серверов; балансировщики; DNS; CDN.
3. **Веб-сервисы:** REST без состояния, API-first.
4. **Масштабирование данных:** репликация (master-slave), шардирование, NoSQL-компромиссы.
5. **Кэширование на всех уровнях:** HTTP-кэш (браузер, прокси, CDN), объектный кэш (Redis/Memcached), кэш приложения; инвалидация — главная трудность.
6. **Кэшировать как можно выше в стеке** — чем ближе к клиенту, тем дешевле.
7. **Асинхронная обработка:** очереди сообщений, развязка, выравнивание пиков; идемпотентность потребителей; порядок сообщений и отравленные сообщения.
8. **Поиск:** выделенные поисковые движки (Elasticsearch), инвертированные индексы.
9. **Автоматизация:** CI/CD, автомасштабирование, мониторинг, агрегация логов.
10. **Принципы проектирования:** простота, слабая связанность, DRY, проектирование под масштаб, самовосстановление.
11. **Приоритизация и культура:** делайте меньше, но важное; автоматизируйте рутину.

**Применение в NotaCode**
- **HTTP-кэширование:** статические ассеты Vite — хэш в имени + `Cache-Control: public, max-age=31536000, immutable`; `index.html` — `no-cache`; неизменяемые версии диаграмм `GET /diagrams/{id}/versions/{vid}` — `Cache-Control: private, max-age=31536000, immutable` + `ETag`; изменяемые ресурсы — `ETag` + `If-None-Match` → `304`.
- **Кэш компиляции** в Redis: ключ `compile:{notation}:{sha256(source)}:{compiler_version}` — без инвалидации (контент-адресованный), TTL 24 ч.
- **CDN** перед статикой и экспортированными файлами (подписанные URL с истечением).
- **Очередь с DLQ** для «отравленных» заданий экспорта.
- **Поиск по диаграммам:** на старте PostgreSQL full-text (`tsvector` по имени, описанию и идентификаторам элементов); выделенный движок — только при доказанной необходимости.

## 8. System Design Interview — Алекс Сюй

**Библиография**
- Alex Xu. *System Design Interview – An Insider's Guide*. Vol. 1. Independently published, 2020. ISBN 979-8664653403.
- Alex Xu, Sahn Lam. *System Design Interview – An Insider's Guide: Volume 2*. ByteByteGo, 2022.
- Рус. изд. (т. 1): Алекс Сюй. *System Design. Подготовка к сложному интервью*. СПб.: Питер, 2022.

**Ключевые принципы**
1. **Четырёхшаговый фреймворк:** уточнить требования и масштаб → высокоуровневый дизайн → детализация узких мест → итоги и компромиссы.
2. **Оценки «на салфетке»:** QPS, объём хранения, пропускная способность; числа задержек, которые должен знать каждый.
3. **Масштабирование с нуля до миллионов:** балансировщик, репликация БД, кэш, CDN, stateless, шардирование, очереди, мониторинг.
4. **Rate limiter:** token bucket, leaking bucket, fixed window, sliding window log, sliding window counter; распределённый вариант на Redis.
5. **Консистентное хэширование** с виртуальными узлами.
6. **Key-value хранилище:** CAP, кворумы (N, W, R), векторные часы, gossip, hinted handoff, Merkle-деревья.
7. **Генератор уникальных ID** (Snowflake: время + машина + последовательность).
8. **Сокращатель URL, веб-краулер, система уведомлений, лента новостей, чат, автодополнение, YouTube, Google Drive** — типовые кейсы.
9. **Google Drive-кейс:** блочное хранение, дедупликация, дельта-синхронизация, уведомления об изменениях (long polling), разрешение конфликтов.
10. **Чат-кейс:** WebSocket, сервис присутствия, хранение сообщений (KV), упорядочивание.
11. **Автодополнение:** префиксное дерево (trie) с топ-k в узлах.
12. (Т. 2) — близость, геопоиск, платёжная система (идемпотентность, reconciliation), распределённая очередь сообщений, мониторинг метрик.

**Применение в NotaCode**
- **Оценка нагрузки (цель v1):** 10 000 DAU, 20 сохранений/пользователь/день → ~200 000 версий/день ≈ 2,3 RPS среднее, пик ×10 ≈ 25 RPS записи; средняя версия 20 КБ (исходник + модель) → ~4 ГБ/день до сжатия. Вывод: одна PostgreSQL с репликой чтения достаточна; нужна политика прореживания автосохранений и TOAST-сжатие.
- **Rate limiting:** распределённый **token bucket** в Redis (Lua-скрипт, атомарно): аноним — 30 запр./мин по IP; авторизованный — 300 запр./мин; `/compile` — 60/мин; `/export` — 10/мин; AI — по токенам/день. Ответ `429` + `Retry-After` + заголовки `RateLimit-Limit/Remaining/Reset`.
- **ID:** UUIDv7 (упорядочен по времени, дружелюбен к B-tree) для всех сущностей и событий.
- **Кейс Google Drive → синхронизация:** контент-хэши для «нет изменений», конфликт = две версии с общим предком → UI сравнения и ручное/трёхстороннее слияние.
- **Кейс автодополнения** — для Monaco: trie по идентификаторам элементов текущего документа + ключевым словам нотации (на клиенте, в Web Worker).

## 9. Distributed Systems Observability — Синди Сридхаран

**Библиография**
- Cindy Sridharan. *Distributed Systems Observability: A Guide to Building Robust Systems*. O'Reilly (отчёт), 2018. ISBN 978-1492033424. Бесплатно (спонсор — Humio).
- Рус. изд.: нет.

**Ключевые принципы**
1. **Наблюдаемость ≠ мониторинг:** мониторинг проверяет известные сбои, наблюдаемость позволяет исследовать неизвестные.
2. **Три столпа:** логи (дискретные события), метрики (агрегаты во времени), трассировки (путь запроса); каждый со своими сильными и слабыми сторонами.
3. **Структурированные логи** (ключ-значение/JSON), а не свободный текст.
4. **Метрики дёшевы при хранении,** хороши для алертинга; проблема высокой кардинальности меток.
5. **Трассировки** показывают причинность и задержки через сервисы; требуют инструментирования и распространения контекста.
6. **Проектирование под отказ:** признать, что система всегда частично сломана.
7. **Тестирование в продакшене** (canary, фичефлаги, теневой трафик) как дополнение к предрелизному тестированию.
8. **Алертинг по симптомам (SLO), а не по причинам;** алерт должен быть срочным, действенным, влияющим на пользователя.
9. **Сэмплирование трасс** (head/tail) для контроля стоимости.
10. **Корреляция сигналов** через общие идентификаторы (trace id в логах).
11. **Инструменты — не культура;** наблюдаемость — свойство системы, закладываемое при проектировании.

**Применение в NotaCode**
- **OpenTelemetry везде** (детали — в `08-devops-testing-ai.md`): авто-инструментирование FastAPI, SQLAlchemy, httpx, Redis; на фронте — `@opentelemetry/sdk-trace-web` для fetch и навигации.
- **Структурированные JSON-логи** (`structlog`): обязательные поля `timestamp`, `level`, `event`, `trace_id`, `span_id`, `request_id`, `user_id_hash`, `diagram_id`; запрещено логировать исходники диаграмм, токены, email.
- **Кардинальность меток метрик:** нельзя ставить `diagram_id`/`user_id` меткой метрики; допустимо — `notation`, `route`, `status_class`.
- **SLO v1:** доступность API 99,5 %/30 дней; p95 `POST /compile` < 300 мс; p95 сохранения версии < 500 мс; ошибки экспорта < 1 %. Алерты — по скорости сжигания бюджета ошибок (burn rate), многооконные.
- **Tail-based sampling** в Collector: 100 % трасс с ошибками и медленных (> 1 с), 10 % остальных.

## 10. The Twelve-Factor App — Адам Уиггинс

**Библиография**
- Adam Wiggins (Heroku). *The Twelve-Factor App*. 2011. https://12factor.net ; рус. перевод: https://12factor.net/ru/
- С 2024 г. методология открыта как open source (github.com/twelve-factor).

**Ключевые принципы (двенадцать факторов)**
1. **Кодовая база:** одна кодовая база в VCS — много развёртываний.
2. **Зависимости:** явно объявлены и изолированы.
3. **Конфигурация:** хранится в переменных окружения.
4. **Сторонние службы:** подключаемые ресурсы (БД, очередь) взаимозаменяемы по URL.
5. **Сборка, релиз, выполнение:** строго разделённые стадии.
6. **Процессы:** приложение — один или несколько процессов без состояния.
7. **Привязка портов:** сервис экспортирует себя через порт.
8. **Параллелизм:** масштабирование через модель процессов.
9. **Одноразовость:** быстрый запуск и корректное завершение (graceful shutdown).
10. **Паритет окружений:** dev/staging/prod максимально похожи.
11. **Логи:** поток событий в stdout.
12. **Административные процессы:** разовые задачи (миграции) в том же окружении, что и приложение.

**Применение в NotaCode**
- **Конфигурация** — только переменные окружения, читаемые `pydantic-settings` (`NOTACODE_DATABASE_URL`, `NOTACODE_REDIS_URL`, `NOTACODE_OAUTH_GITHUB_CLIENT_ID`…); на фронте — `import.meta.env.VITE_*` только для несекретных значений. `.env.example` в репозитории, `.env` — в `.gitignore`.
- **Зависимости:** `uv`/`poetry` с lock-файлом; `package-lock.json`/`pnpm-lock.yaml`; Docker-образы с закреплёнными digest.
- **Сборка ≠ релиз:** один образ, собранный в CI, продвигается dev → staging → prod с разной конфигурацией.
- **Процессы без состояния,** файлы экспорта — в объектном хранилище (S3/MinIO), не на локальном диске.
- **Graceful shutdown:** uvicorn/gunicorn обрабатывает SIGTERM, воркеры дочитывают текущее задание и не берут новые (таймаут 30 с).
- **Логи — в stdout** (JSON), сбор — Collector/Docker driver.
- **Миграции** — `alembic upgrade head` отдельным одноразовым контейнером перед выкаткой.
- **Паритет:** `docker compose` локально с теми же PostgreSQL/Redis версиями, что в проде.

## 11. The DevOps Handbook — Ким, Хамбл, Дебуа, Уиллис

**Библиография**
- Gene Kim, Jez Humble, Patrick Debois, John Willis. *The DevOps Handbook: How to Create World-Class Agility, Reliability, and Security in Technology Organizations*. IT Revolution Press, 2016. 2-е изд. (+ Nicole Forsgren): 2021. ISBN 978-1950508402.
- Рус. изд.: *Руководство по DevOps. Как добиться гибкости, надёжности и безопасности мирового уровня в технологических компаниях*. М.: Манн, Иванов и Фербер, 2018.

**Ключевые принципы**
1. **Три пути:** поток (flow), обратная связь (feedback), непрерывное обучение и эксперименты.
2. **Поток:** визуализировать работу, ограничивать WIP, уменьшать размер партий, устранять ограничения и потери.
3. **Конвейер развёртывания:** каждое изменение проходит автоматическую сборку, тесты и может быть выкачено.
4. **Непрерывная интеграция:** trunk-based development, маленькие частые коммиты в основную ветку.
5. **Автоматизированное тестирование** быстрое и надёжное; пирамида тестов; «андон-шнур» — остановить линию при красной сборке.
6. **Развёртывания с низким риском:** отделить развёртывание от релиза (фичефлаги, dark launch, canary, blue-green).
7. **Телеметрия везде:** метрики бизнеса, приложения, инфраструктуры; самообслуживание.
8. **Обратная связь:** пир-ревью, парное программирование, быстрый откат.
9. **Безвинные постмортемы** (blameless), обучение на инцидентах.
10. **Встроенная безопасность (DevSecOps):** проверки безопасности в пайплайне, анализ зависимостей.
11. **Метрики DORA:** частота развёртываний, время выполнения изменений, частота отказов изменений, время восстановления.
12. **Архитектура для низкого риска релизов:** слабая связанность, Strangler.

**Применение в NotaCode**
- **Trunk-based development:** короткоживущие ветки (≤ 2 дней), PR обязательно с ревью, `main` всегда выкатываемый; защищённая ветка с обязательными проверками.
- **Конвейер:** lint (ruff/eslint, запрет комментариев) → typecheck (mypy --strict / tsc --noEmit) → unit+integration (100 % покрытия) → e2e Playwright → security (pip-audit, npm audit, Trivy, CodeQL/Semgrep, gitleaks) → build image → deploy staging → smoke → manual/auto promote prod.
- **Андон:** красный `main` — приоритет №1 команды, мёрж других PR блокируется.
- **Отделение развёртывания от релиза** фичефлагами (нотации, AI-ассистент, синхронизация с Drive).
- **DORA-метрики** собираются из GitHub API; цель — развёртывания ежедневно, lead time < 1 дня, CFR < 15 %, MTTR < 1 ч.
- **Постмортемы** — `docs/postmortems/YYYY-MM-DD-title.md`, безвинный формат.
