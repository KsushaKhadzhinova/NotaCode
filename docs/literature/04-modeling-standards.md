# 04. Стандарты и нотации моделирования

> Для каждой нотации: библиография, ключевые идеи, **базовые элементы** и **формальные правила, пригодные для валидатора** (с кодами правил), а также «Применение в NotaCode».
> Коды правил имеют вид `<NOTATION>-<AREA>-<NNN>`; серьёзность: **E** — ошибка (модель некорректна по стандарту), **W** — предупреждение (нарушение методических рекомендаций), **I** — подсказка стиля. Пометка **[fix]** — для правила есть автоисправление.
> Тексты стандартов не воспроизводятся; правила сформулированы своими словами на основе знания спецификаций.

---

## Общие решения для всех нотаций

- Каждая нотация — плагин `NotationPlugin` с метамоделью (типы элементов, атрибуты, допустимые связи `source_type × edge_type × target_type`, кратности) и набором правил-`Specification`.
- Проверки делятся на уровни: **L0 синтаксис DSL** (парсер) → **L1 структурные** (типы, обязательные атрибуты, допустимые связи — генерируются из метамодели) → **L2 семантические** (правила ниже) → **L3 поведенческие/анализ** (достижимость, тупики, живость — для Petri/BPMN, с ограничением по времени).
- Autofix обязан быть **идемпотентным**, **детерминированным** и **минимальным** (меняет только то, что нужно), результат — новая версия, а не мутация.
- Каждое сообщение: код, серьёзность, текст на языке UI, ссылка на элемент (диапазон в DSL + id на холсте), ссылка на раздел стандарта (номер пункта, без цитирования текста).

## 1. UML Distilled — Мартин Фаулер

**Библиография**
- Martin Fowler. *UML Distilled: A Brief Guide to the Standard Object Modeling Language*. 3rd ed. Addison-Wesley, 2003 (copyright 2004). ISBN 978-0321193681.
- Рус. изд.: Мартин Фаулер. *UML. Основы. Краткое руководство по стандартному языку объектного моделирования*. 3-е изд. СПб.: Символ-Плюс, 2004 (переиздания 2005–2006).

**Ключевые принципы**
1. **Три способа использования UML:** эскиз (sketch), чертёж (blueprint), язык программирования; большинству полезен эскиз.
2. **Показывайте только важное** — диаграмма не обязана быть полной.
3. **Диаграмма классов** — ядро; точки зрения: концептуальная, спецификации, реализации.
4. **Диаграмма последовательностей** — для одного сценария; не пытайтесь показать всю логику ветвлений.
5. **Диаграммы деятельности** хороши для бизнес-процессов и параллелизма.
6. **Диаграммы состояний** — для объектов с выраженным жизненным циклом.
7. **Use case** — текст важнее диаграммы.
8. **Ассоциация, агрегация, композиция:** агрегация семантически слаба; композиция означает владение и совместное время жизни.
9. **Нотационная строгость** важна для чертежей и генерации кода, не для эскизов.
10. **UML — не процесс;** он совместим с итеративной разработкой.

**Применение в NotaCode**
- **Два режима валидации UML:** *sketch* (только E-правила структуры) и *blueprint* (все правила, включая W/I). Режим — атрибут диаграммы в DSL (`@mode blueprint`).
- Диаграмма последовательностей по умолчанию предупреждает при > 3 уровнях вложенных фрагментов (`UML-SEQ-W-010`) — «один сценарий на диаграмму».

## 2. UML 2.5.1 (OMG) / ISO/IEC 19505

**Библиография**
- Object Management Group. *OMG Unified Modeling Language (OMG UML), Version 2.5.1*. formal/17-12-05, December 2017. https://www.omg.org/spec/UML/2.5.1/
- ISO/IEC 19505-1:2012 и 19505-2:2012 *Information technology — OMG UML — Part 1: Infrastructure; Part 2: Superstructure* (соответствуют UML 2.4.1).
- Связанные: OCL 2.4 (formal/14-02-03), XMI 2.5.1, UML Diagram Interchange (DI/DD), MOF 2.5.1.
- Рус. изд. спецификации: нет официального перевода.

**Ключевые идеи**
1. UML определён метамоделью на MOF; абстрактный синтаксис + ограничения на OCL + нотация + семантика.
2. **14 типов диаграмм:** 7 структурных и 7 поведенческих (включая 4 диаграммы взаимодействия).
3. Диаграмма — лишь представление элементов модели; один элемент может быть на нескольких диаграммах.
4. Обмен моделями — **XMI**; обмен геометрией — **UML DI**.
5. Механизм расширения — **профили и стереотипы**.
6. Правила корректности (well-formedness) задаются ограничениями OCL в спецификации метаклассов.

**Типы диаграмм и базовые элементы**

| # | Диаграмма | Базовые элементы |
|---|---|---|
| 1 | Class | Class, Interface, DataType, Enumeration, Attribute, Operation, Association (+ends, multiplicity, navigability), Aggregation/Composition, Generalization, Realization, Dependency, AssociationClass |
| 2 | Object | InstanceSpecification, Slot, Link |
| 3 | Package | Package, PackageImport, ElementImport, PackageMerge, Dependency |
| 4 | Component | Component, Port, provided/required Interface, Connector (assembly, delegation) |
| 5 | Composite Structure | StructuredClassifier, Part (Property), Port, Connector, Collaboration, CollaborationUse |
| 6 | Deployment | Node, Device, ExecutionEnvironment, Artifact, Deployment, CommunicationPath, Manifestation |
| 7 | Profile | Profile, Stereotype, Extension, Metaclass reference, ProfileApplication |
| 8 | Use Case | Actor, UseCase, Subject (system boundary), Association, Include, Extend (+ExtensionPoint), Generalization |
| 9 | Activity | InitialNode, ActivityFinalNode, FlowFinalNode, Action, ObjectNode/Pin, ControlFlow, ObjectFlow, DecisionNode, MergeNode, ForkNode, JoinNode, ActivityPartition, InterruptibleActivityRegion, ExceptionHandler, CallBehaviorAction, Send/AcceptEventAction |
| 10 | State Machine | Region, State (simple/composite/submachine), FinalState, Pseudostates (initial, deepHistory, shallowHistory, join, fork, junction, choice, entryPoint, exitPoint, terminate), Transition (trigger[guard]/effect), ProtocolStateMachine |
| 11 | Sequence | Lifeline, Message (synch, asynch, reply, create, delete, lost, found), ExecutionSpecification, CombinedFragment (alt, opt, loop, par, break, critical, neg, assert, strict, seq, ignore, consider), InteractionUse (ref), Gate, StateInvariant, DestructionOccurrence |

**Формальные правила для валидатора (выборка, основа — well-formedness rules спецификации)**
- `UML-CLS-E-001` Обобщение не образует циклов (классификатор не может быть собственным предком).
- `UML-CLS-E-002` Обобщение только между классификаторами совместимого вида (класс ↔ класс, интерфейс ↔ интерфейс, актёр ↔ актёр, use case ↔ use case).
- `UML-CLS-E-003` Кратность: нижняя граница ≥ 0, верхняя ≥ нижней или `*`.
- `UML-CLS-E-004` Композиция: на композитном конце кратность верхней границы ≤ 1 (часть принадлежит не более чем одному целому одновременно).
- `UML-CLS-E-005` Имена членов (атрибутов/операций-сигнатур) уникальны в пространстве имён классификатора, с учётом унаследованных (конфликт — ошибка) **[fix: переименовать с суффиксом]**.
- `UML-CLS-E-006` Абстрактная операция допустима только в абстрактном классе или интерфейсе **[fix: пометить класс абстрактным]**.
- `UML-CLS-E-007` Интерфейс не имеет экземпляров и не содержит реализаций методов; реализовывать интерфейс (Realization) может только поведенческий классификатор.
- `UML-CLS-E-008` Ассоциация имеет ≥ 2 концов; n-арная (> 2) ассоциация не может быть агрегацией/композицией.
- `UML-CLS-W-009` Имена классов — существительные в UpperCamelCase; атрибутов/операций — lowerCamelCase (стиль, I/W).
- `UML-PKG-E-001` Имена элементов, непосредственно принадлежащих пакету, уникальны (с учётом вида элемента); импорты не создают конфликтов.
- `UML-PKG-W-002` Циклическая зависимость пакетов.
- `UML-UC-E-001` Актёр связан только с use case (или компонентом/классом) ассоциациями; актёр не может ассоциироваться с другим актёром.
- `UML-UC-E-002` Include/Extend — только между use case; граф include ацикличен.
- `UML-UC-E-003` Extend ссылается на существующую точку расширения расширяемого use case.
- `UML-UC-W-004` Use case без связанного актёра (и не включаемый/не расширяющий) **[fix: предложение связать]**.
- `UML-ACT-E-001` У InitialNode нет входящих рёбер; у ActivityFinalNode/FlowFinalNode нет исходящих.
- `UML-ACT-E-002` Ребро ObjectFlow соединяет объектные узлы/пины, ControlFlow — не оканчивается на пине данных без указания control.
- `UML-ACT-E-003` DecisionNode: 1 входящее (+ опционально decisionInputFlow), ≥ 1 исходящих; MergeNode: ≥ 1 входящих, 1 исходящее; ForkNode: 1 входящее; JoinNode: 1 исходящее.
- `UML-ACT-W-004` Исходящие рёбра DecisionNode должны иметь охранные условия, ровно одно может быть `[else]` **[fix: добавить `[else]` к единственному ребру без условия]**.
- `UML-ACT-W-005` Каждый узел достижим из некоторого InitialNode (или из входного параметра) и ведёт к финальному узлу.
- `UML-ACT-W-006` Несбалансированные fork/join (fork без соответствующего join) — предупреждение о возможных «висящих» токенах.
- `UML-SM-E-001` Регион имеет не более одного initial pseudostate; у initial ровно один исходящий переход без триггера и без охраны.
- `UML-SM-E-002` У FinalState нет исходящих переходов; у регионов/состояний — нет входящих в initial.
- `UML-SM-E-003` Choice: ≥ 1 исходящих; охраны исходящих переходов choice/junction — допускается `[else]`.
- `UML-SM-E-004` Fork/join pseudostates: переходы ведут в/из разных ортогональных регионов одного составного состояния.
- `UML-SM-E-005` History pseudostate — только в составном состоянии, максимум одна глубокая и одна поверхностная на регион.
- `UML-SM-W-006` Недостижимое состояние; состояние без выхода (кроме финального) — тупик.
- `UML-SM-W-007` Недетерминизм: два перехода из одного состояния по одному триггеру без взаимоисключающих охран.
- `UML-SEQ-E-001` Reply-сообщение следует за соответствующим синхронным вызовом на тех же линиях жизни.
- `UML-SEQ-E-002` После DestructionOccurrence на линии жизни не может быть событий.
- `UML-SEQ-E-003` Операнды `alt` имеют охраны; не более одного `[else]`; `opt`/`break` — один операнд; `loop` — один операнд с (min,max).
- `UML-SEQ-E-004` Create-сообщение направлено на начало линии жизни (линия не имеет более ранних событий).
- `UML-SEQ-W-005` Сообщение ссылается на операцию, отсутствующую у классификатора получателя (в режиме blueprint).
- `UML-COM-E-001` Номера последовательности уникальны и образуют корректную иерархию (1, 1.1, 1.2, 2).
- `UML-CMP-E-001` Assembly-коннектор соединяет required-интерфейс с provided-интерфейсом совместимого типа.
- `UML-CMP-E-002` Delegation-коннектор соединяет внешний порт с внутренней частью совместимого направления (provided → provided, required → required).
- `UML-DEP-E-001` Artifact развёртывается только на Node/ExecutionEnvironment/Device; Node вкладывается только в Node.
- `UML-PRF-E-001` Stereotype расширяет метакласс (Extension); применение стереотипа к элементу допустимо, только если его метакласс расширен и профиль применён к пакету.
- `UML-TIM-E-001` Временные ограничения: min ≤ max; моменты на линии времени монотонны.
- `UML-IOV-E-001` Interaction Overview содержит только узлы управления деятельности и взаимодействия/ссылки на взаимодействия.

**Применение в NotaCode**
- 14 диаграмм — 14 подплагинов `uml.class`, `uml.object`, …; общая UML-метамодель (упрощённый срез UML 2.5.1) — Shared Kernel между ними (класс из class-диаграммы переиспользуется на sequence через ссылку `Lifeline : Order`).
- **Импорт/экспорт XMI 2.5.1** (через ACL): при экспорте — только элементы, выражаемые стандартно; кастомные стили — в `xmi:Extension extender="NotaCode"`.
- Правила с OCL-природой реализуются как Python-`Specification`; ссылка на номер пункта спецификации хранится в метаданных правила.

## 3. BPMN 2.0.2 (OMG) / ISO/IEC 19510

**Библиография**
- Object Management Group. *Business Process Model and Notation (BPMN), Version 2.0.2*. formal/13-12-09, December 2013. https://www.omg.org/spec/BPMN/2.0.2/
- ISO/IEC 19510:2013 *Information technology — Object Management Group Business Process Model and Notation*.
- Рус. изд.: официального перевода нет.

**Ключевые идеи**
1. Четыре вида диаграмм: **Process (оркестрация)**, **Collaboration**, **Choreography**, **Conversation**.
2. Пять категорий элементов: Flow Objects (Events, Activities, Gateways), Data, Connecting Objects, Swimlanes, Artifacts.
3. Семантика выполнения задана через **токены**.
4. Обмен — **BPMN XML (XSD) + BPMN DI** (геометрия).
5. **Классы соответствия:** Process Modeling (Descriptive, Analytic, Common Executable), Process Execution, BPEL Process Execution, Choreography Modeling.
6. Sequence Flow не пересекает границы пула; между пулами — только Message Flow.

**Базовые элементы**
- **События:** Start / Intermediate (catching, throwing, boundary interrupting/non-interrupting) / End. Триггеры: None, Message, Timer, Error, Escalation, Cancel, Compensation, Conditional, Link, Signal, Terminate, Multiple, Parallel Multiple.
- **Активности:** Task (None, User, Manual, Service, Send, Receive, Script, Business Rule), Sub-Process (embedded, event, transaction, ad-hoc), Call Activity; маркеры: loop, multi-instance (parallel/sequential), compensation.
- **Шлюзы:** Exclusive (XOR), Inclusive (OR), Parallel (AND), Event-Based (exclusive/parallel), Complex.
- **Данные:** Data Object (+collection), Data Input/Output, Data Store, Data Association.
- **Соединения:** Sequence Flow (conditional, default), Message Flow, Association.
- **Дорожки:** Pool (Participant), Lane (вложенные).
- **Артефакты:** Group, Text Annotation.
- **Хореография:** Choreography Task (инициирующий и отвечающий участники, сообщения), Sub-Choreography, Call Choreography; события и шлюзы с ограничениями.
- **Conversation:** Conversation, Sub-Conversation, Call Conversation, Conversation Link, Participant.

**Формальные правила для валидатора**
*Структура процесса*
- `BPMN-EVT-E-001` Start Event не имеет входящих Sequence Flow; End Event — исходящих.
- `BPMN-EVT-E-002` Boundary event прикреплён ровно к одной активности, не имеет входящих Sequence Flow, имеет ≥ 1 исходящих (кроме compensation — связь Association с обработчиком).
- `BPMN-EVT-E-003` Error/Cancel/Compensation start event допустимы только в Event Sub-Process; Cancel boundary — только на Transaction Sub-Process.
- `BPMN-EVT-E-004` Error boundary event всегда прерывающий; Error end event не может быть в event sub-process без обработчика вверх по иерархии (W).
- `BPMN-EVT-E-005` Link events: для каждого throwing Link существует catching Link с тем же именем в том же уровне процесса.
- `BPMN-EVT-E-006` Top-level процесс, содержащий события-триггеры для старта, использует только допустимые типы (None, Message, Timer, Conditional, Signal, Multiple, Parallel Multiple).
- `BPMN-EVT-W-007` Процесс без Start/End Event при наличии хотя бы одного из них — стандарт требует пару (если есть Start, должен быть End, и наоборот) **[fix: добавить недостающее событие]**.
- `BPMN-FLW-E-001` Sequence Flow соединяет только Flow Objects в пределах одного Pool (одного процесса) и не пересекает границу Sub-Process.
- `BPMN-FLW-E-002` Message Flow соединяет элементы **разных** Pool (или пул как «чёрный ящик»); не соединяет элементы одного пула.
- `BPMN-FLW-E-003` Источник Message Flow — throwing message event, Send/User/Service/Manual Task, sub-process или пул; цель — catching message event, Receive/User/Service/Manual Task, sub-process, пул. Start/End Event не могут быть соответственно источником/целью неверного направления.
- `BPMN-FLW-E-004` Conditional Sequence Flow из активности обозначается мини-ромбом; из Parallel Gateway условные потоки запрещены.
- `BPMN-FLW-E-005` Default flow — только из Exclusive/Inclusive/Complex Gateway или активности; не более одного default на узел; default не имеет условия.
- `BPMN-FLW-W-006` Узел без входящих потоков (кроме Start/boundary/event-subprocess-start) — недостижим **[fix: предложить соединить с предыдущим узлом по порядку в DSL]**; узел без исходящих (кроме End) — неявное завершение.
- `BPMN-GW-E-001` Шлюз — либо разветвляющий (1 вход, ≥ 2 выхода), либо сливающий (≥ 2 входа, 1 выход); смешанный допустим стандартом, но рекомендуется разделять (W `BPMN-GW-W-002` **[fix: разделить на два шлюза]**).
- `BPMN-GW-E-003` Исходящие потоки разветвляющего Exclusive/Inclusive шлюза имеют условия, кроме default.
- `BPMN-GW-W-004` Exclusive/Inclusive шлюз без default flow — риск тупика во время исполнения **[fix: пометить последний поток как default]**.
- `BPMN-GW-E-005` Event-Based Gateway: ≥ 2 исходящих; цели — только intermediate catching events (Message, Timer, Signal, Conditional) или Receive Task, не смешивая Receive Task и Message event; у целей нет других входящих потоков; условия на потоках запрещены.
- `BPMN-GW-W-006` Несоответствие типов разветвления и слияния (Parallel split → Exclusive join) — возможен повторный запуск/тупик; проверка через анализ блочной структуры и L3-анализ сети Петри.
- `BPMN-ACT-E-001` Receive Task с `instantiate=true` — единственный допустимый вход процесса без Start Event.
- `BPMN-ACT-E-002` Call Activity ссылается на существующий процесс/глобальную задачу.
- `BPMN-ACT-E-003` Compensation-активность не имеет входящих/исходящих Sequence Flow.
- `BPMN-SUB-E-001` Event Sub-Process не имеет входящих/исходящих Sequence Flow, содержит ровно один Start Event с триггером.
- `BPMN-SUB-E-002` Ad-hoc Sub-Process не содержит Start/End Event.
*Дорожки и коллаборация*
- `BPMN-LAN-E-001` Lane — только внутри Pool; каждый Flow Object процесса с лейнами принадлежит ровно одному (листовому) лейну.
- `BPMN-COL-E-001` В Collaboration ≥ 2 Participant (Pool); не более одного «белого ящика» на процесс.
- `BPMN-COL-W-002` Пул-«чёрный ящик» не содержит элементов процесса.
*Данные и артефакты*
- `BPMN-DAT-E-001` Data Association соединяет Data Object/Store с активностью/событием (не с шлюзом); Association — с артефактами.
- `BPMN-ART-E-001` Group и Text Annotation не участвуют в Sequence/Message Flow.
*Хореография*
- `BPMN-CHO-E-001` У Choreography Task ровно два участника: один инициирующий, один (или более для multi-instance participant) отвечающий; с ≤ 2 сообщениями (инициирующее + ответ).
- `BPMN-CHO-E-002` Правило инициатора: инициатор задачи обязан участвовать в предыдущей задаче (sequential flow constraint) — иначе необнаруживаемая последовательность.

*Conversation*
- `BPMN-CNV-E-001` Conversation Link соединяет Conversation-узел с Participant; ≥ 2 участника на Conversation.

## 4. Real-Life BPMN / Camunda BPMN guide

**Библиография**
- Jakob Freund, Bernd Rücker. *Real-Life BPMN: Using BPMN and DMN to Analyze, Improve, and Automate Processes in Your Company*. 4th ed. Camunda, 2019. ISBN 978-1086302097.
- Camunda BPMN reference и best practices: https://camunda.com/bpmn/reference/ ; https://docs.camunda.io/docs/components/best-practices/
- Также: Bruce Silver. *BPMN Method and Style*. 2nd ed. Cody-Cassidy Press, 2011.
- Рус. изд.: нет.

**Ключевые принципы**
1. **Рамочная модель Camunda BPMN Framework:** стратегический уровень (обзор), операционный (человеческий и технический потоки), реализационный.
2. **Стратегическая модель** — один пул, 5–10 шагов, «счастливый путь», без шлюзов-деталей.
3. **Человеческий поток отдельно от технического:** участники как пулы, коллаборация между ними.
4. **Именование:** задачи — глагол + объект; события — существительное + причастие (состояние); шлюзы XOR — вопрос, исходящие потоки — ответы.
5. **Читаемость слева направо**, счастливый путь по прямой, исключения — вниз.
6. **Явные шлюзы**, одинаковый тип для разветвления и слияния; избегать смешанных шлюзов.
7. **Моделировать конечные события явно** с различными результатами.
8. **Boundary events** для таймаутов и ошибок вместо проверочных шлюзов после задачи.
9. **Пулы как «чёрные ящики»** для внешних участников.
10. **Не злоупотреблять лейнами** для систем — лейны это роли/ответственность.
11. **Исполняемость — отдельный уровень:** не каждая модель должна быть исполняемой.
12. **DMN** для бизнес-правил вместо каскада шлюзов.

**Применение в NotaCode**
- Методические правила `BPMN-STY-*` (см. выше) берутся отсюда; по умолчанию серьёзность W и отключаемы в профиле проверок.
- **Автораскладка BPMN** следует «слева направо, счастливый путь по прямой»: основной путь (самая длинная цепочка от Start к «успешному» End) выравнивается по одной горизонтали, исключения — ниже.
- Шаблоны уровней «стратегический/операционный» — готовые сниппеты DSL.

## 5. Сети Петри

### 5.1. Petri Net Theory and the Modeling of Systems — Джеймс Питерсон

**Библиография**
- James L. Peterson. *Petri Net Theory and the Modeling of Systems*. Prentice-Hall, 1981. ISBN 978-0136619833.
- Рус. изд.: Дж. Питерсон. *Теория сетей Петри и моделирование систем*. М.: Мир, 1984.

**Ключевые принципы**
1. Сеть Петри — двудольный ориентированный граф: **позиции (places)** и **переходы (transitions)**, дуги только между разными типами.
2. **Маркировка** — распределение фишек (токенов) по позициям; состояние системы.
3. **Правило срабатывания:** переход разрешён, если в каждой входной позиции фишек не меньше веса дуги; срабатывание изымает и добавляет фишки.
4. Моделирование параллелизма, конфликта, синхронизации, взаимного исключения.
5. **Свойства:** ограниченность (k-ограниченность, безопасность), живость, достижимость, покрываемость, консервативность, обратимость.
6. **Дерево достижимости/покрываемости** (с ω для неограниченных позиций).
7. **Матричный подход:** матрица инцидентности, уравнение состояний.
8. **Подклассы:** автоматные сети, маркированные графы, сети свободного выбора, простые сети.
9. **Расширения:** ингибиторные дуги, приоритеты, время — увеличивают выразительную мощность (до машины Тьюринга) и делают анализ неразрешимым.
10. Языки сетей Петри и их соотношение с формальными языками.

### 5.2. Murata, "Petri Nets: Properties, Analysis and Applications"

**Библиография**
- Tadao Murata. *Petri Nets: Properties, Analysis and Applications*. Proceedings of the IEEE, vol. 77, no. 4, pp. 541–580, April 1989. DOI: 10.1109/5.24143.
- Рус. изд.: нет (классическая обзорная статья).

**Ключевые принципы**
1. Формальное определение `PN = (P, T, F, W, M0)`.
2. **Поведенческие свойства** (зависят от M0): достижимость, ограниченность, живость (L0–L4), обратимость и home state, покрываемость, устойчивость (persistence), синхронная дистанция, справедливость.
3. **Структурные свойства** (не зависят от M0): структурная живость, управляемость, структурная ограниченность, консервативность, повторяемость, согласованность.
4. **Методы анализа:** дерево покрываемости, матричные уравнения, редукции (сохраняющие свойства правила упрощения), инварианты.
5. **P-инварианты** (`y^T · C = 0`) — сохраняющиеся взвешенные суммы фишек; **T-инварианты** (`C · x = 0`) — циклические последовательности срабатываний.
6. **Сифоны и ловушки** — для анализа живости сетей свободного выбора (теорема Коммонера).
7. **Подклассы и разрешимость:** для маркированных графов и сетей свободного выбора есть полиномиальные критерии.
8. **Временные и стохастические сети:** детерминированные задержки, экспоненциальные распределения (SPN, GSPN) → марковские цепи.
9. **Высокоуровневые сети:** цветные, предикатно-переходные.
10. **Применения:** протоколы, производственные системы, параллельные программы, СУБД.

### 5.3. ISO/IEC 15909 — High-level Petri Nets, PNML

**Библиография**
- ISO/IEC 15909-1:2019 *Systems and software engineering — High-level Petri nets — Part 1: Concepts, definitions and graphical notation* (1-е изд. — 2004).
- ISO/IEC 15909-2:2011 *Part 2: Transfer format* (PNML — Petri Net Markup Language).
- ISO/IEC 15909-3:2021 *Part 3: Extensions and structuring mechanisms*.
- Сайт PNML: https://www.pnml.org ; Kurt Jensen, Lars M. Kristensen. *Coloured Petri Nets: Modelling and Validation of Concurrent Systems*. Springer, 2009.

**Ключевые идеи**

5. Модульность и иерархия (Part 3): страницы, fusion places, substitution transitions (в духе CPN Tools).

## 6. IDEF0 — FIPS PUB 183 / IEEE Std 1320.1

**Библиография**
- NIST. *Integration Definition for Function Modeling (IDEF0)*. FIPS PUB 183, 21 December 1993 (отменён как FIPS в 2008, остаётся де-факто стандартом).
- IEEE Std 1320.1-1998 *IEEE Standard for Functional Modeling Language — Syntax and Semantics for IDEF0* (reaffirmed 2004).
- Рус.: Р 50.1.028-2001 *Информационные технологии поддержки жизненного цикла продукции. Методология функционального моделирования* (Госстандарт России).

**Ключевые идеи**
1. Функциональная модель системы как иерархия **блоков-функций** и **стрелок ICOM**: Input (слева), Control (сверху), Output (справа), Mechanism (снизу), + Call (снизу, вниз).
2. Модель имеет **назначение (purpose)**, **точку зрения (viewpoint)** и **границы (scope)**.
3. **Контекстная диаграмма A-0** — ровно один блок; стрелки на границе.
4. **Декомпозиция:** каждый блок может детализироваться дочерней диаграммой (A0, A1, A11…), содержащей 3–6 блоков.
5. **Туннелирование стрелок** (скобки) — стрелки, не показываемые на родителе/потомке.
6. **ICOM-кодирование граничных стрелок** дочерней диаграммы (I1, C2, O1, M1) обеспечивает связь с родителем.
7. Блоки располагаются по диагонали «лестницей» по доминированию.
8. Стрелки могут разветвляться и сливаться; метки на сегментах.

**Базовые элементы:** Box (функция: имя-глагольная фраза, номер узла), Arrow (Input, Control, Output, Mechanism, Call), Boundary arrow, Internal arrow, Branch/Join, Tunnel (у источника/у приёмника), Diagram (node number, title, C-number), Node tree, FEO/Text/Glossary pages.

**Формальные правила для валидатора**
- `IDEF0-DIA-E-001` A-0 содержит ровно один блок.
- `IDEF0-DIA-E-002` Дочерняя диаграмма содержит от 3 до 6 блоков (FIPS 183); без автоисправления — только подсказка по перегруппировке.
- `IDEF0-BOX-E-001` У каждого блока ≥ 1 Control и ≥ 1 Output.
- `IDEF0-BOX-W-002` Блок без Input допустим; без Mechanism — допустим (W-подсказка при детальных моделях).
- `IDEF0-BOX-E-003` Стрелки подходят к сторонам по ролям: Input — левая сторона (вход), Control — верх (вход), Output — правая (выход), Mechanism — низ (вход), Call — низ (выход). **[fix: перепривязать к корректной стороне]**
- `IDEF0-BOX-W-004` Имя блока — глагол/глагольная фраза; стрелки — существительные.
- `IDEF0-BOX-E-005` Нумерация блоков на диаграмме уникальна (1…6), номер узла = номер родителя + номер блока (A1 → A11, A12).
- `IDEF0-ARR-E-001` Каждая стрелка (сегмент) имеет метку (допускается наследование метки при ветвлении/слиянии, если однозначно).
- `IDEF0-ARR-E-002` Output блока не может напрямую возвращаться Input/Control/Mechanism того же блока без явного обоснования — W (обратная связь допустима, но должна огибать блок).
- `IDEF0-DEC-E-001` Каждая граничная стрелка дочерней диаграммы соответствует стрелке родительского блока с тем же ICOM-кодом и ролью (I→I, C→C, O→O, M→M), либо помечена туннелем **[fix: создать недостающие граничные стрелки/туннели]**.
- `IDEF0-DEC-E-002` Каждая стрелка родительского блока, не туннелированная у приёмника, присутствует на дочерней диаграмме.
- `IDEF0-MOD-E-001` У модели заданы purpose, viewpoint, scope (контекст A-0).
- `IDEF0-STY-I-001` Раскладка блоков по диагонали сверху-слева вниз-вправо.

**Применение в NotaCode**
- Плагин `idef0`: одна DSL-модель = дерево диаграмм; навигация по узлам A-0 → A0 → A1…; **проверка согласованности декомпозиции** (ICOM) — ключевая ценность.
- Специальная раскладка: блоки по диагонали, ортогональная маршрутизация стрелок с входом по ролям сторон.
- Экспорт: SVG/PNG каждой страницы + «node tree»; текстовый формат модели — собственный (единого XML-стандарта обмена нет).

## 7. IDEF1X — FIPS PUB 184 / IEEE Std 1320.2

**Библиография**
- NIST. *Integration Definition for Information Modeling (IDEF1X)*. FIPS PUB 184, 21 December 1993.
- IEEE Std 1320.2-1998 *IEEE Standard for Conceptual Modeling Language — Syntax and Semantics for IDEF1X97 (IDEFobject)*.
- Рус.: официального ГОСТ-перевода нет; широко описан в отечественной литературе по ERwin.

**Ключевые идеи**
1. Модель данных из **сущностей, атрибутов, связей**; ориентирована на реляционную реализацию.
2. **Независимые** сущности (прямоугольник) и **зависимые** (скруглённые углы) — зависимость по идентификации.
3. **Идентифицирующая связь** (сплошная линия) — PK родителя входит в PK потомка; **неидентифицирующая** (пунктир) — FK вне PK.
4. **Кардинальность** на стороне потомка: по умолчанию 0..n (точка), P (1..n), Z (0..1), n (ровно n).
5. **Категориальные связи (обобщение):** полные/неполные, с дискриминатором.
6. **Неспецифические связи (многие-ко-многим)** допустимы только на уровне ER-представления; в полной модели разрешаются ассоциативной сущностью.
7. **Уровни:** ER (сущности/связи), Key-Based (ключи), Fully Attributed (все атрибуты, 3НФ).
8. **Правила ключей:** PK, альтернативные ключи (AKn), внешние ключи (FK), роли (role names), унификация миграции ключей.
9. **Нормализация:** атрибуты не повторяются, не имеют значений NULL в PK, одна сущность — один факт.

**Базовые элементы:** Entity (independent/dependent), Attribute (PK, AK, FK, IE — inversion entry), Identifying/Non-identifying Relationship (mandatory/optional), Cardinality, Categorization (complete/incomplete, discriminator), Non-specific Relationship, Role name, Domain.

**Формальные правила для валидатора**
- `IDEF1X-ENT-E-001` У каждой сущности (на уровне Key-Based и выше) есть первичный ключ.
- `IDEF1X-ENT-E-002` Сущность — потомок идентифицирующей связи является зависимой **[fix: пометить зависимой]**; зависимая сущность имеет хотя бы одну идентифицирующую связь с родителем.
- `IDEF1X-ENT-E-003` Имена сущностей уникальны в модели; имена атрибутов уникальны в модели (IDEF1X требует глобально уникальных имён атрибутов, при миграции — роли) **[fix: role name]**.
- `IDEF1X-REL-E-001` Идентифицирующая связь: FK мигрирует в PK потомка; сторона родителя обязательна (родитель не может быть NULL).
- `IDEF1X-REL-E-002` Неидентифицирующая связь: FK вне PK; при опциональной — FK допускает NULL.
- `IDEF1X-REL-E-003` Циклы идентифицирующих связей запрещены (сущность не может идентифицироваться через саму себя).
- `IDEF1X-REL-W-004` Неспецифическая (M:N) связь на уровне Key-Based/Fully Attributed **[fix: заменить ассоциативной сущностью с двумя идентифицирующими связями]**.
- `IDEF1X-CAT-E-001` Категориальная связь: у родовой сущности есть дискриминатор; категории взаимоисключающие; PK категорий = PK родовой сущности; категория имеет одну родовую сущность в одном кластере.
- `IDEF1X-KEY-E-001` Атрибуты PK не допускают NULL; AK уникальны; каждый FK соответствует PK (или AK) родителя по количеству и доменам.
- `IDEF1X-KEY-W-002` Унификация: один и тот же мигрирующий FK от двух путей объединяется, если так задумано (иначе — роли).
- `IDEF1X-NRM-W-001` Повторяющиеся группы атрибутов (адрес1, адрес2…) — подсказка на нормализацию.

**Применение в NotaCode**
- Плагин `idef1x` использует общее ядро ER-моделирования (см. ER/Crow's foot) с IDEF1X-представлением; переключение нотации отображения без изменения модели (где возможно).
- **Экспорт в SQL DDL** (PostgreSQL) на уровне Fully Attributed: PK/AK → `PRIMARY KEY`/`UNIQUE`, FK → `REFERENCES` с `ON DELETE` по типу связи.

## 8. IDEF3 — KBSI, 1995

**Библиография**
- Richard J. Mayer, Christopher P. Menzel, Michael K. Painter, Paula S. deWitte, Thomas Blinn, Benjamin Perakath. *Information Integration for Concurrent Engineering (IICE) IDEF3 Process Description Capture Method Report*. Knowledge Based Systems, Inc. (KBSI), for Armstrong Laboratory, Wright-Patterson AFB, September 1995.
- Рус.: описан в отечественной литературе (методические материалы по BPwin/AllFusion Process Modeler); официального стандарта нет.

**Ключевые идеи**
1. Метод фиксации **описаний процессов** со слов экспертов — сценарии, а не предписания.
2. Две схемы: **Process Flow Description Diagram (PFDD)** — процесс-ориентированная, и **Object State Transition Network (OSTN)** — объект-ориентированная.
3. **UOB (Unit of Behavior)** — единица поведения (действие, процесс, событие), с номером и описанием (elaboration).
4. **Связи (links):** предшествования (precedence), отношения (relational, пунктир), объектного потока.
5. **Перекрёстки (junctions):** AND (&), OR (O), XOR (X); синхронные и асинхронные; разветвляющие (fan-out) и сливающие (fan-in).
6. **Ссылки (referents)** на другие UOB, сценарии, объекты, переходы — для перехода между уровнями и повторного использования.
7. **Декомпозиция UOB** — несколько альтернативных декомпозиций (точек зрения).
8. **OSTN:** состояния объекта (круги) и переходные дуги, к которым прикрепляются UOB-ссылки, вызывающие переход.

**Базовые элементы**
- PFDD: UOB (прямоугольник с номером), Precedence Link (сплошная стрелка), Relational Link (пунктир), Object Flow Link (двойная стрелка), Junction (&, O, X; синхронный — двойная вертикальная черта), Referent (UOB/SCENARIO/OBJECT/GOTO/NOTE), Elaboration.
- OSTN: Object State (круг), State Transition Arc, UOB-referent на дуге, Entry/Exit conditions.

**Формальные правила для валидатора**
- `IDEF3-UOB-E-001` Номера UOB уникальны в модели; номер декомпозиции ссылается на существующий родительский UOB.
- `IDEF3-UOB-W-002` Имя UOB — глагольная фраза.
- `IDEF3-LNK-E-001` Precedence Link соединяет UOB/junction с UOB/junction (не с referent как целью цепочки потока, кроме GOTO).
- `IDEF3-LNK-E-002` Связи в PFDD ацикличны по precedence, кроме явных циклов через GOTO-referent (W при неявном цикле).
- `IDEF3-JNC-E-001` Junction либо разветвляющий (1 вход, ≥ 2 выхода), либо сливающий (≥ 2 входа, 1 выход).
- `IDEF3-JNC-E-002` XOR-разветвление не может быть синхронным (синхронность имеет смысл для AND/OR).
- `IDEF3-JNC-W-003` Разветвление и соответствующее слияние одного типа (& — &, X — X, O — O) **[fix: предложить тип слияния]**.
- `IDEF3-REF-E-001` Referent ссылается на существующий UOB/сценарий/объект; GOTO — на UOB в той же схеме или на другой сценарий.
- `IDEF3-OST-E-001` В OSTN дуги соединяют только состояния; UOB-referent прикрепляется к дуге перехода.
- `IDEF3-OST-W-002` Состояние без входящих (кроме начального) или без исходящих (кроме конечного) переходов.

**Применение в NotaCode**
- Плагины `idef3.pfdd` и `idef3.ostn`; UOB из PFDD можно ссылаться из OSTN (перекрёстные ссылки между диаграммами одной модели, как `Shared Kernel` модели).
- Трансляция PFDD в сеть Петри для проверки согласованности junction-ов (аналогично BPMN).

## 9. DFD — Гейн–Сарсон, Йордон/Де Марко

**Библиография**
- Chris Gane, Trish Sarson. *Structured Systems Analysis: Tools and Techniques*. Prentice-Hall, 1979. ISBN 978-0138545475.
- Tom DeMarco. *Structured Analysis and System Specification*. Yourdon Press, 1978 (Prentice-Hall, 1979). ISBN 978-0138543808.
- Edward Yourdon. *Modern Structured Analysis*. Prentice-Hall, 1989. ISBN 978-0135986240. (Близкая по теме книга на русском: Э. Йордон, К. Аргила. *Структурные модели в объектно-ориентированном анализе и проектировании*. М.: Лори, 1999.)
- Рус.: официального стандарта нет; методика изложена в учебниках по CASE (напр., Г. Н. Калянов. *CASE-технологии. Консалтинг в автоматизации бизнес-процессов*. М.: Горячая линия-Телеком, 2002).

**Ключевые идеи**
1. DFD показывает **движение данных**, а не управление и не последовательность.
2. Четыре элемента: **внешняя сущность** (терминатор), **процесс**, **хранилище данных**, **поток данных**.
3. **Нотации:** Йордон/Де Марко — процесс-круг, хранилище — две параллельные линии; Гейн–Сарсон — процесс-скруглённый прямоугольник с номером, хранилище — открытый прямоугольник с идентификатором (D1), внешняя сущность — квадрат с тенью.
4. **Контекстная диаграмма (уровень 0)** — один процесс (система) и внешние сущности.
5. **Иерархическая декомпозиция** (уровни 1, 2…) с нумерацией 1, 1.1, 1.1.1.
6. **Балансировка:** входы/выходы процесса-родителя совпадают с граничными потоками дочерней диаграммы.
7. **Словарь данных** описывает состав потоков и хранилищ (нотация `=`, `+`, `[ | ]`, `{ }`, `( )`).
8. **Мини-спецификации** (структурированный английский, таблицы решений) для примитивных процессов.
9. 7±2 процесса на диаграмме.

**Базовые элементы:** External Entity, Process (номер, глагольное имя), Data Store (ID, существительное), Data Flow (имя-существительное, направление), (Yourdon real-time: Control Flow, Control Process — опционально).

**Формальные правила для валидатора**
- `DFD-FLW-E-001` Поток данных не соединяет две внешние сущности напрямую.
- `DFD-FLW-E-002` Поток данных не соединяет внешнюю сущность и хранилище напрямую (через процесс) **[fix: вставить процесс-заглушку]**.
- `DFD-FLW-E-003` Поток данных не соединяет два хранилища напрямую.
- `DFD-FLW-E-004` Каждый поток (кроме потоков в/из хранилища, где допустимо имя хранилища) имеет имя.
- `DFD-PRC-E-001` У процесса ≥ 1 входящий и ≥ 1 исходящий поток («чёрная дыра» — только входы, «чудо» — только выходы).
- `DFD-PRC-W-002` «Серая дыра»: выходы процесса не могут быть получены из его входов (эвристика по словарю данных).
- `DFD-STR-W-001` Хранилище только с записью или только с чтением на всех диаграммах модели.
- `DFD-CTX-E-001` Контекстная диаграмма: ровно один процесс, нет хранилищ (по Йордону — хранилища на контексте не показываются).
- `DFD-BAL-E-001` Балансировка: множество входных/выходных потоков дочерней диаграммы (с учётом словаря данных — разложение потока) совпадает с потоками родительского процесса **[fix: добавить недостающие граничные потоки]**.
- `DFD-NUM-E-001` Нумерация процессов иерархична и уникальна (1, 1.1, 1.2).
- `DFD-STY-W-001` Процессов на диаграмме 3–9.
- `DFD-STY-W-002` Имя процесса — глагол + объект; имя потока/хранилища — существительное.

**Применение в NotaCode**
- Плагин `dfd` с переключаемой нотацией отображения `gane-sarson | yourdon-demarco` (одна модель, два стиля фигур).
- **Словарь данных** — часть DSL (`data CustomerOrder = customer_id + {order_line} + (discount)`), используется для балансировки с разложением потоков.

## 10. ER-модель — Питер Чен, 1976

**Библиография**
- Peter Pin-Shan Chen. *The Entity-Relationship Model — Toward a Unified View of Data*. ACM Transactions on Database Systems, vol. 1, no. 1, pp. 9–36, March 1976. DOI: 10.1145/320434.320440.
- Рус.: изложение в учебниках по БД (напр., К. Дж. Дейт. *Введение в системы баз данных*. 8-е изд. М.: Вильямс, 2005).

**Ключевые идеи**
1. Мир состоит из **сущностей** и **связей** между ними; у обоих есть **атрибуты** (значения из доменов).
2. **Множества сущностей** (прямоугольник), **множества связей** (ромб), **атрибуты** (овалы).
3. **Роли** сущностей в связи; рекурсивные связи через роли.
4. **Кардинальность** связи (1:1, 1:N, M:N), указываемая на рёбрах.
5. **Слабые сущности** (двойной прямоугольник) — существование и идентификация через владельца; **идентифицирующая связь** — двойной ромб.
6. **Первичный ключ** — подчёркнутые атрибуты; частичный ключ слабой сущности — пунктирное подчёркивание.
7. Модель — концептуальная; отображается на реляционную, сетевую, иерархическую.
8. Расширения (EER): обобщение/специализация, многозначные (двойной овал), составные, производные (пунктирный овал) атрибуты, участие (полное — двойная линия).

**Базовые элементы (Chen/EER):** Entity, Weak Entity, Relationship, Identifying Relationship, Attribute (key, partial key, multivalued, composite, derived), Role, Cardinality (1, N, M), Participation (total/partial), (min,max)-нотация, ISA/Specialization (disjoint/overlapping, total/partial).

### Crow's foot (Information Engineering)

**Библиография**
- Gordon C. Everest. *Basic Data Structure Models Explained with a Common Example*. Proc. Fifth Texas Conference on Computing Systems, Austin, 1976 (первое описание «inverted arrow», позднее — crow's foot).
- James Martin, Clive Finkelstein. *Information Engineering*. Savant Institute, 1981; James Martin. *Information Engineering, Book II: Planning and Analysis*. Prentice Hall, 1990.
- Barker R. *CASE*Method: Entity Relationship Modelling*. Addison-Wesley, 1990 (нотация Баркера/Oracle).

**Ключевые идеи и элементы**
1. Сущность — прямоугольник со списком атрибутов (PK/FK), связь — линия без ромба.
2. На каждом конце — пара символов: внешний — максимум (`|` один, «воронья лапка» — много), внутренний — минимум (`O` ноль, `|` один).
3. Комбинации: `||` ровно один, `O|` ноль или один, `|<` один или много, `O<` ноль или много.
4. Связь читается в обе стороны глагольной фразой.
5. Естественно отражает логическую/физическую модель (атрибуты внутри прямоугольника).

**Уровни ERD в NotaCode**
| Уровень | Содержимое | Разрешено |
|---|---|---|
| Концептуальный | Сущности, связи, ключевые бизнес-атрибуты | M:N, без типов данных, без FK |
| Логический | Все атрибуты, PK/AK/FK, нормализация до 3НФ | M:N — W (разрешать ассоциативной сущностью) |
| Физический | Таблицы, колонки, типы СУБД, индексы, ограничения | M:N — E; обязательны типы, имена по правилам СУБД |

**Формальные правила для валидатора (ERD, все нотации Chen / Crow's foot / UML-class-as-ERD)**
- `ERD-ENT-E-001` Имена сущностей уникальны; атрибутов — уникальны в сущности.
- `ERD-ENT-E-002` (логический/физический) У каждой не-слабой сущности есть PK.
- `ERD-WEAK-E-001` Слабая сущность участвует ≥ 1 в идентифицирующей связи с полным участием и кардинальностью «много к одному» к владельцу; имеет частичный ключ.
- `ERD-REL-E-001` (Chen) Связь соединяет ≥ 2 концов (сущности или роли); рекурсивная связь — роли на обоих концах обязательны.
- `ERD-REL-E-002` Кардинальность каждого конца задана и корректна: min ≤ max, min ∈ {0,1,…}, max ∈ {1,…,N}.
- `ERD-REL-E-003` (физический) M:N запрещена **[fix: ассоциативная таблица с составным PK из двух FK]**.
- `ERD-REL-W-004` Двойная обязательность 1:1 (`||—||`) — вероятно одна сущность (подсказка на слияние).
- `ERD-REL-W-005` Цикл обязательных связей — невозможность вставки без отложенных ограничений.
- `ERD-ATT-E-001` (физический) Каждая колонка имеет тип СУБД из допустимого списка диалекта; PK-колонки NOT NULL.
- `ERD-ATT-E-002` FK ссылается на PK/UNIQUE целевой таблицы с совпадающим числом и типами колонок **[fix: скорректировать тип FK]**.
- `ERD-ATT-W-003` Многозначный атрибут на логическом уровне → вынести в сущность (1НФ) **[fix]**.
- `ERD-ATT-W-004` Составной атрибут на физическом уровне → разложить на колонки **[fix]**.
- `ERD-ISA-E-001` Специализация: подтипы наследуют PK супертипа; ациклична; помечена disjoint/overlapping и total/partial.
- `ERD-NAM-W-001` (физический) Имена в стиле диалекта (PostgreSQL: `snake_case`, ≤ 63 символов, не зарезервированные слова) **[fix: нормализовать имя]**.
- `ERD-NRM-I-001` Эвристики нормализации: транзитивные зависимости по объявленным FD (если FD заданы в DSL) → 3НФ-подсказка.

**Применение в NotaCode**
- **Единая ER-модель, несколько нотаций представления** (`chen`, `crowsfoot`, `uml`, `idef1x`, `barker`) и три уровня (`conceptual`, `logical`, `physical`); переход уровней — трансформации с autofix (концептуальная M:N → логическая ассоциативная сущность).
- **Экспорт физической модели в SQL DDL** (PostgreSQL, MySQL, SQLite диалекты) и **импорт из DDL** (reverse engineering через `sqlglot`).
