## 1. Clean Architecture — Роберт Мартин

**Библиография**
- Robert C. Martin. *Clean Architecture: A Craftsman's Guide to Software Structure and Design*. Prentice Hall, 2017. ISBN 978-0134494166.
- Рус. изд.: *Чистая архитектура. Искусство разработки программного обеспечения*. СПб.: Питер, 2018.

**Ключевые принципы**
1. **Цель архитектуры** — минимизировать человеческие усилия на создание и сопровождение системы.
2. **SOLID** на уровне модулей: SRP (одна причина для изменения = один актор), OCP, LSP, ISP, DIP.
3. **Правило зависимостей:** зависимости в исходном коде направлены только внутрь — к политикам высокого уровня (сущности → сценарии использования → адаптеры интерфейсов → фреймворки и драйверы).
4. **Сущности (Entities)** — корпоративные бизнес-правила; **Use Cases** — прикладные правила конкретного приложения.
5. **Фреймворк, БД, веб — детали.** Их решение можно откладывать; архитектура «кричит» о предметной области, а не о фреймворке (Screaming Architecture).
6. **Границы и полиморфизм:** пересечение границы — через интерфейс, объявленный внутренним слоем (инверсия зависимостей).
7. **Принципы связности компонентов:** REP (повторное использование = выпуск), CCP (общее закрытие), CRP (общее повторное использование).
8. **Принципы сочетаемости компонентов:** ADP (нет циклов), SDP (зависимость в сторону стабильности), SAP (стабильные компоненты абстрактны).
9. **Humble Object** — трудно тестируемое (UI, БД) отделяется в «скромный» объект с минимальной логикой.
10. **Частичные границы** — допустимы, когда полная граница преждевременна.
11. **Тесты — часть системы** и тоже подчиняются правилу зависимостей; хрупкость тестов — архитектурная проблема.
12. **«Главный» компонент (Main)** — самый грязный модуль, собирающий зависимости (composition root).

Цитата: «The database is a detail» — одна из глав книги.

**Применение в NotaCode**
- **Структура бэкенда (Python):**
  ```
  backend/app/
    domain/          сущности, value objects, доменные события, порты (Protocol)
    application/     use cases (CreateDiagram, CompileSource, ValidateDiagram, ApplyAutofix, RollbackVersion, ExportDiagram)
    notations/       плагины нотаций (чистый домен: метамодели, правила, autofix)
    adapters/        http (FastAPI routers), persistence (SQLAlchemy), storage (github, gdrive), ai (stub)
    main.py          composition root
  ```
- **Правило зависимостей проверяется автоматически:** `import-linter` (контракты `layers` и `forbidden`) — `domain` не импортирует `fastapi`, `sqlalchemy`, `pydantic` (кроме value-типов, если решено ADR), `httpx`.
- **Фронтенд** — тот же принцип: `src/domain` (модель диаграммы, чистые функции), `src/features/*`, `src/infrastructure` (API-клиент, IndexedDB), `src/ui`. Правило `eslint-plugin-boundaries`.
- **Humble Object:** компоненты React — «скромные» (рендер + вызов хука), логика — в чистых функциях и сторах, покрытых юнит-тестами; обработчики FastAPI — не длиннее 5 строк (распаковать запрос → вызвать use case → сериализовать ответ).
- **Нет циклов между пакетами** (ADP) — проверка `import-linter` + `madge --circular` на фронте.

## 2. Patterns of Enterprise Application Architecture — Мартин Фаулер

**Библиография**
- Martin Fowler et al. *Patterns of Enterprise Application Architecture*. Addison-Wesley, 2002. ISBN 978-0321127426.
- Рус. изд.: *Шаблоны корпоративных приложений*. М.: Вильямс, 2006 (переиздания).

**Ключевые принципы**
1. **Слои:** представление, предметная область, источник данных.
2. **Организация доменной логики:** Transaction Script (простые случаи), Domain Model (сложная логика), Table Module, Service Layer (граница приложения).
3. **Паттерны источника данных:** Table/Row Data Gateway, Active Record, Data Mapper.
4. **Unit of Work** — отслеживает изменённые объекты в рамках бизнес-транзакции и фиксирует их одним коммитом.
5. **Identity Map** — каждый объект загружается один раз за сессию.
6. **Lazy Load** — отложенная загрузка связанных данных (с риском N+1).
7. **Repository** — коллекционно-подобный интерфейс к агрегатам поверх Data Mapper.
8. **Паттерны конкурентного доступа:** Optimistic Offline Lock (версия записи), Pessimistic Offline Lock, Coarse-Grained Lock.
9. **Session State:** клиентское, серверное, в БД — с компромиссами.
10. **Distribution:** первый закон распределённых объектов — не распределяйте их; Remote Facade и DTO для грубозернистых вызовов.
11. **Value Object, Money, Special Case (Null Object), Registry, Plugin, Service Stub, Gateway.**
12. **Serialized LOB** — сохранение графа объектов как одного поля (в NotaCode — JSONB).

**Применение в NotaCode**
- **Domain Model + Service Layer** для ядра (валидация, версии); Transaction Script допустим только для тривиальных CRUD-настроек пользователя.
- **Data Mapper + Repository + Unit of Work** через SQLAlchemy 2.0 (явный `session`), доменные сущности не наследуют ORM-модели (отдельные `orm.py` таблицы и мапперы).
- **Optimistic Offline Lock:** у диаграммы поле `revision`; `PUT /diagrams/{id}` требует `If-Match: "<etag>"`; при несовпадении — `412 Precondition Failed` и клиент предлагает merge через diff.
- **Serialized LOB = JSONB:** нормализованная модель диаграммы (узлы/рёбра/стили) хранится в `diagram_versions.model jsonb`, исходник DSL — в `source text`; индексы только на реально запрашиваемые пути (GIN по `jsonb_path_ops`).
- **Special Case:** `AnonymousUser`, `EmptyDiagram`, `NoAiAssistant` вместо `None`.
- **Remote Facade + DTO:** API отдаёт грубозернистые ресурсы (`DiagramDetail` с последней версией), чтобы UI не делал десятки запросов.
- **Service Stub:** `StubAiAssistant` — точная реализация порта `AiAssistant`, возвращающая детерминированные ответы; тесты и демо не зависят от LLM.

## 3. Fundamentals of Software Architecture — Марк Ричардс, Нил Форд

**Библиография**
- Mark Richards, Neal Ford. *Fundamentals of Software Architecture: An Engineering Approach*. O'Reilly, 2020. ISBN 978-1492043454. (2-е изд. — O'Reilly, 2025.)
- Рус. изд.: *Фундаментальный подход к программной архитектуре: паттерны, свойства, проверенные методы*. СПб.: Питер, 2023.

**Ключевые принципы**
1. **Первый закон архитектуры:** всё — компромисс. **Второй:** «почему» важнее, чем «как».
2. **Архитектурные характеристики («-ilities»)** — масштабируемость, доступность, эластичность, тестируемость, развёртываемость и т.д.; выбирать немногие ключевые, а не все сразу.
3. **Архитектурный квант** — независимо развёртываемая единица с высокой функциональной связностью и синхронной связанностью.
4. **Модульность:** связность (cohesion), связанность (coupling), коннасценция (connascence) — статическая и динамическая; сила, локальность, степень.
5. **Фитнес-функции** — автоматизированные проверки архитектурных характеристик.
6. **Стили:** layered, pipeline, microkernel (плагины), service-based, event-driven, space-based, orchestration-driven SOA, microservices — с оценочными таблицами.
7. **Microkernel** — ядро + плагины; хорош для продуктовых систем с расширяемыми возможностями.
8. **Service-based** — несколько крупных сервисов с общей БД; прагматичная середина между монолитом и микросервисами.
9. **ADR (Architecture Decision Records)** — фиксировать решение, контекст, последствия.
10. **Анализ рисков архитектуры** (risk storming), диаграммирование и презентация архитектуры.
11. **Роль архитектора:** технический лидер, переговорщик, отвечает за решения, а не за технологии ради технологий.
12. **Компонентное мышление:** выделение компонентов по предметной области (domain partitioning) предпочтительнее технического разбиения.

Цитата: «Everything in software architecture is a trade-off» (Первый закон, Ричардс и Форд).

**Применение в NotaCode**
- **Ключевые характеристики (топ-7):** корректность (валидаторы), расширяемость (новые нотации), тестируемость (100%), доступность/офлайн (PWA), отзывчивость редактора (< 100 мс на инкрементальный парс), безопасность (OAuth, OWASP), наблюдаемость.
- **Стиль:** **microkernel внутри модульного монолита** — ядро (компилятор, модель, версии) + плагины нотаций (`uml.*`, `bpmn`, `erd`, `idef0`, `idef3`, `idef1x`, `dfd`, `petri.*`, `freeform`). Регистрация через entry points (`importlib.metadata.entry_points(group="notacode.notations")`) и реестр на фронте.
- **Эволюция к service-based:** выносим по мере необходимости — `export-worker` (тяжёлый рендер PNG/PDF), `ai-gateway`, `sync-worker` (GitHub/Drive). Общая PostgreSQL, раздельные схемы.
- **Фитнес-функции в CI:** import-linter, покрытие 100%, отсутствие комментариев, бюджет бандла (`size-limit`), Lighthouse ≥ 90, p95 компиляции 1 000 элементов < 300 мс (pytest-benchmark).
- **ADR:** `docs/architecture/adr/NNNN-title.md` (формат Nygard: контекст, решение, статус, последствия).
- **Domain partitioning:** папки верхнего уровня — `diagrams`, `versions`, `compiler`, `notations`, `storage-sync`, `export`, `identity`, `assistant`, а не `controllers/services/models`.

## 4. Software Architecture: The Hard Parts — Форд, Ричардс, Садаладж, Дехгани

**Библиография**
- Neal Ford, Mark Richards, Pramod Sadalage, Zhamak Dehghani. *Software Architecture: The Hard Parts — Modern Trade-Off Analyses for Distributed Architectures*. O'Reilly, 2021. ISBN 978-1492086895.
- Рус. изд.: *Современный подход к программной архитектуре: сложные компромиссы*. СПб.: Питер, 2023.

**Ключевые принципы**
1. **Нет «лучших практик» — есть компромиссы** в конкретном контексте; анализ через сравнение вариантов.
2. **Статическая и динамическая связанность** квантов; коммуникация (синхр./асинхр.), согласованность (атомарная/итоговая), координация (оркестрация/хореография).
3. **Восемь «саг»** — комбинации трёх измерений (например, Epic Saga: синхронно, атомарно, оркестрация).
4. **Декомпозиция монолита:** компонентная (component-based) или тактическое разветвление (tactical forking).
5. **Драйверы дезинтеграции** сервиса: область ответственности, частота изменений, масштабируемость, отказоустойчивость, безопасность, расширяемость.
6. **Драйверы интеграции:** транзакции ACID, рабочие процессы, общий код, связь данных.
7. **Декомпозиция данных:** владение таблицами, общее владение, совместное владение; паттерны доступа к данным (межсервисный вызов, репликация колонок, реплицированный кэш, data domain).
8. **Повторное использование кода:** копирование, общая библиотека, общий сервис, sidecar/service mesh.
9. **Контракты:** строгие против слабых (loose contracts), consumer-driven contracts.
10. **Распределённые транзакции** и управление состояниями саги; компенсации.
11. **Аналитические данные:** Data Mesh как отдельная ось.
12. **ADR и фитнес-функции** как инструменты управления.

**Применение в NotaCode**
- **Решение о выделении сервиса** принимается только по драйверам дезинтеграции (фиксируется в ADR): `export-worker` — масштабируемость и отказоустойчивость (падение Chromium-рендера не должно ронять API); `ai-gateway` — безопасность (секреты провайдеров) и частота изменений.
- **Данные — владение по контексту:** таблицы `diagrams/diagram_versions` принадлежат контексту *Diagramming*; `users/identities` — *Identity*; `sync_links` — *Storage Sync*. Прямые JOIN между схемами разных контекстов запрещены; нужны данные — через порт/API или реплицированное представление.
- **Синхронизация с GitHub/Drive — «Fairy Tale Saga»** (асинхронно, итоговая согласованность, оркестрация): оркестратор `SyncJob` со статусами `pending → pushing → pushed | failed` и компенсацией (пометка конфликта, без удаления локальной версии).
- **Общий код:** метамодели нотаций — общая библиотека `notacode-notations` (Python) и сгенерированный TS-пакет; не общий сервис.
- **Контракты:** слабые JSON-контракты с `additionalProperties` на чтении (tolerant reader), строгие на записи; consumer-driven тесты (Pact или schemathesis по OpenAPI) между фронтом и API.

## 5. Software Architecture for Developers / модель C4 — Саймон Браун

**Библиография**
- Simon Brown. *Software Architecture for Developers. Volume 1: Technical leadership and the balance with agility*; *Volume 2: Visualise, document and explore your software architecture*. Leanpub, 2012–2024 (постоянно обновляется).
- Официальный сайт модели: https://c4model.com ; инструмент Structurizr: https://structurizr.com (DSL: https://docs.structurizr.com/dsl).
- Рус. изд.: официального перевода нет.

**Ключевые принципы**
1. **Архитектура — дело разработчиков;** «достаточно» предварительного проектирования, а не ноль и не всё.
2. **Модель C4 — четыре уровня абстракции:** System Context → Containers → Components → Code.
3. **System Context:** система, пользователи (persons) и внешние системы.
4. **Container:** отдельно запускаемая/развёртываемая единица (SPA, API, БД, очередь) — не путать с Docker-контейнером.
5. **Component:** группа связанных функций за чётким интерфейсом внутри контейнера.
6. **Code:** UML-класс-диаграммы — только по необходимости, желательно генерировать.
7. **Дополнительные диаграммы:** System Landscape, Dynamic, Deployment.
8. **Нотационно-независимость, но с правилами:** у каждого элемента — имя, тип, технология, описание; у каждой стрелки — однонаправленная подпись с глаголом и протоколом; легенда обязательна.
9. **Модель, а не рисунок:** диаграммы — проекции единой модели (diagrams as code), чтобы не расходились.
10. **Архитектурные драйверы:** функциональные требования, качественные атрибуты, ограничения, принципы.
11. **Документация «достаточная и живая»**, рядом с кодом.
12. **Риск-ориентированный подход** (risk-storming) к объёму проектирования.

**Применение в NotaCode**
- **Документация архитектуры NotaCode — в C4**, в `docs/architecture/c4/` как Structurizr DSL (или собственный DSL NotaCode — dogfooding):
  - **L1 Context:** Пользователь (аналитик/архитектор), NotaCode, GitHub, Google Drive, OAuth-провайдеры, LLM-провайдер (будущий), GlitchTip.
  - **L2 Containers:** PWA (React+Vite, Service Worker, IndexedDB), API (FastAPI), Export Worker, PostgreSQL, Redis (кэш, rate limit, очередь), Object Storage (экспорты), OpenTelemetry Collector.
  - **L3 Components (API):** Compiler, Validator Engine, Autofix Engine, Version Service, Storage Sync, Export Service, Identity, Assistant Port.
  - **L4:** генерируется из кода по требованию.
- **Каждая стрелка подписана** глаголом и протоколом: «Отправляет исходник DSL [HTTPS/JSON]».
- **Продуктовая фича:** C4 поддерживается как дополнительная нотация (на базе free-form + стереотипы) с правилами валидатора: у Container обязательна технология, стрелки без подписи — предупреждение.

## 6. MonolithFirst — Мартин Фаулер (статья)

**Библиография**
- Martin Fowler. *MonolithFirst*. martinfowler.com/bliki, 3 June 2015. https://martinfowler.com/bliki/MonolithFirst.html
- Контрапункт: Stefan Tilkov. *Don't start with a monolith*. martinfowler.com, 2015. https://martinfowler.com/articles/dont-start-monolith.html
- Рус. изд.: нет (есть любительские переводы).

**Ключевые принципы**
1. Почти все успешные микросервисные истории начинались с монолита, который затем разрезали.
2. Системы, изначально построенные как микросервисы, часто попадали в серьёзные проблемы.
3. **Цена микросервисов** (сетевые сбои, согласованность, операционная сложность) оправдана только для сложных систем.
4. **Границы контекстов трудно угадать заранее;** рефакторинг границ между сервисами дороже, чем между модулями.
5. **Скорость проверки гипотезы (YAGNI)** важнее на ранней стадии.
6. **Варианты:** модульный монолит → постепенное отделение по краям (strangler); либо «жертвенный» монолит.
7. **Начинать с грубых сервисов** и дробить позже.
8. Контраргумент Тилкова: если границы известны хорошо, начинать с отдельных частей может быть проще, чем резать монолит.

**Применение в NotaCode**
- **Старт — модульный монолит** (один деплой FastAPI + один SPA), с границами модулей по bounded contexts и контролем import-linter. Это «distributed-ready», но не «distributed-first».
- **Критерии выделения сервиса** (все — измеримые): независимое масштабирование (очередь экспорта > N заданий), изоляция сбоев (рендер PNG), разные требования безопасности (ключи LLM), независимый цикл релизов.
- **Внутримодульное взаимодействие** уже сейчас — через порты и доменные события (in-process bus), чтобы вынос в отдельный процесс заменил только транспорт (outbox + брокер).

## 7. Domain-Driven Design — Эрик Эванс

**Библиография**
- Eric Evans. *Domain-Driven Design: Tackling Complexity in the Heart of Software*. Addison-Wesley, 2003 (copyright 2004). ISBN 978-0321125217.
- Рус. изд.: Эрик Эванс. *Предметно-ориентированное проектирование (DDD). Структуризация сложных программных систем*. М.: Вильямс, 2010.
- Краткий справочник: *Domain-Driven Design Reference* (Evans, 2015, CC BY 4.0).

**Ключевые принципы**
1. **Единый язык (Ubiquitous Language)** — общий словарь экспертов и разработчиков, используемый в коде, тестах, UI, документах.
2. **Модельно-ориентированное проектирование:** код и модель — одно и то же.
3. **Сущности (Entities)** — идентичность сохраняется во времени; **Value Objects** — определяются значениями, неизменяемы.
4. **Агрегаты** — граница согласованности с корнем; ссылки извне только на корень; одна транзакция — один агрегат.
5. **Фабрики** — создание сложных агрегатов; **Репозитории** — иллюзия коллекции агрегатов в памяти.
6. **Доменные сервисы** — операции, не принадлежащие ни одной сущности.
7. **Ограниченный контекст (Bounded Context)** — явная граница применимости модели.
8. **Карта контекстов:** Shared Kernel, Customer/Supplier, Conformist, Anticorruption Layer, Open Host Service, Published Language, Separate Ways, Partnership, Big Ball of Mud.
9. **Стратегическая дистилляция:** Core Domain, Generic и Supporting subdomains; инвестировать лучшие силы в ядро.
10. **Гибкий дизайн (Supple Design):** Intention-Revealing Interfaces, Side-Effect-Free Functions, Assertions, Conceptual Contours, Standalone Classes, Closure of Operations.
11. **Спецификация (Specification)** — бизнес-правило как объект-предикат, комбинируемый логически.
12. **Крупномасштабная структура:** Responsibility Layers, Knowledge Level, Pluggable Component Framework.
13. **Непрерывная интеграция внутри контекста** и защита целостности модели.

Цитата: «Ubiquitous Language» — термин самой книги; суть — один язык в речи и коде.

**Применение в NotaCode**
- **Core domain:** компилятор DSL + семантическая валидация/autofix нотаций. **Supporting:** версии и diff, раскладка, экспорт. **Generic:** идентичность (OAuth), хранилища, телеметрия — покупаем/берём готовое.
- **Bounded contexts:**
  1. *Authoring* (DSL-исходник, парсинг, LSP-диагностики);
  2. *Modeling* (семантическая модель нотаций, валидация, autofix) — отдельная модель на каждую нотацию (Petri-сеть и BPMN-процесс — разные языки);
  3. *Diagram Layout & Rendering* (геометрия, стили, холст);
  4. *Versioning* (версии, diff, rollback);
  5. *Storage Sync* (GitHub, Google Drive, устройство);
  6. *Export/Import* (SVG/PNG/BPMN XML/PNML/XMI/SQL DDL);
  7. *Identity & Access*;
  8. *Assistant* (AI).
- **Карта контекстов:** Authoring → Modeling — Customer/Supplier; внешние форматы (BPMN XML, PNML, XMI, draw.io XML) — **Published Language** с **ACL** (импорт никогда не протаскивает чужую модель в домен); GitHub/Drive — **ACL**; метамодели нотаций — **Shared Kernel** между фронтом и бэком (генерируемые).
- **Агрегаты:** `Diagram` (корень; id, владелец, нотация, указатель на head-версию) и `DiagramVersion` (неизменяемый; исходник, модель, родитель, автор, время, хэш). Правка = новая версия; агрегаты ссылаются по ID.
- **Правила валидатора = Specification:** `class ExclusiveGatewayHasDefaultFlow(Specification[BpmnGateway])`, комбинируемые `and_/or_/not_`; каждое правило имеет код, серьёзность, сообщение и опциональный `Autofix`.
- **Единый язык в коде:** термины стандартов без перевода и «улучшений»: `SequenceFlow`, `MessageFlow`, `Lane`, `Place`, `Transition`, `Arc`, `Token`, `ICOM`, `UnitOfBehavior`, `Junction`, `Entity`, `Relationship`, `Cardinality`. Глоссарий — `docs/theory/glossary.md`.

## 8. Implementing Domain-Driven Design — Вон Вернон

**Библиография**
- Vaughn Vernon. *Implementing Domain-Driven Design*. Addison-Wesley, 2013. ISBN 978-0321834577.
- Рус. изд.: Вон Вернон. *Реализация методов предметно-ориентированного проектирования*. М.: Вильямс, 2016.
- Также: V. Vernon. *Domain-Driven Design Distilled*. Addison-Wesley, 2016 (рус.: *Предметно-ориентированное проектирование: самое основное*, Вильямс, 2017).

**Ключевые принципы**
1. **Стратегия прежде тактики:** сначала субдомены и контексты, потом сущности.
2. **Правила проектирования агрегатов:** моделируйте истинные инварианты в границах согласованности; проектируйте маленькие агрегаты; ссылайтесь на другие агрегаты по идентификатору; используйте итоговую согласованность за пределами границы.
3. **Доменные события** — факты прошлого, именуются глаголом в прошедшем времени; несут идентификаторы и минимум данных.
4. **Публикация событий надёжно:** событие сохраняется в той же транзакции, что и агрегат (Event Store / outbox), затем пересылается.
5. **Интеграция контекстов:** REST (Open Host Service), обмен сообщениями, ACL с трансляторами.
6. **Гексагональная архитектура (порты и адаптеры)** как естественное окружение DDD.
7. **CQRS** — разделение модели записи и модели чтения при необходимости.
8. **Event Sourcing** — состояние как свёртка событий; применять избирательно.
9. **Модули** по понятиям домена, а не по техническим типам.
10. **Сервисы приложения** тонкие: транзакция, безопасность, оркестрация; логика — в домене.
11. **Идемпотентные получатели** — дедупликация сообщений по идентификатору события.
12. **Фабрики на корне агрегата** и **репозитории, ориентированные на коллекцию или на хранение**.

**Применение в NotaCode**
- **Маленькие агрегаты:** `Diagram` не содержит список всех версий в памяти; `DiagramVersion` — отдельный агрегат, ссылается на `diagram_id` и `parent_version_id`.
- **Доменные события:** `DiagramCreated`, `DiagramVersionCommitted`, `DiagramRolledBack`, `ValidationCompleted`, `ExportRequested`, `ExportCompleted`, `SyncRequested`, `SyncCompleted`, `SyncFailed`. Схема — `event_id (UUIDv7)`, `occurred_at`, `aggregate_id`, `aggregate_version`, `type`, `payload`.
- **Transactional outbox:** таблица `outbox_events` пишется в той же транзакции, что и `diagram_versions`; релэй (фоновой воркер, `SELECT ... FOR UPDATE SKIP LOCKED`) публикует в Redis Streams/брокер; получатели идемпотентны (`processed_events(event_id PRIMARY KEY)`).
- **Лёгкий CQRS:** запись — через агрегаты; чтение списка диаграмм и истории — прямыми SQL-проекциями (`DiagramListView`), без загрузки агрегатов.
- **Event Sourcing не используем для всего,** но история версий по сути append-only лог: rollback = новая версия с содержимым старой (история не переписывается).
- **Гексагональная архитектура:** порты `DiagramRepository`, `VersionRepository`, `EventPublisher`, `ExternalStorage`, `Renderer`, `AiAssistant`, `Clock`, `IdGenerator` (последние два — для детерминированных тестов).

## 9. Architecture Patterns with Python («Cosmic Python») — Гарри Персиваль, Боб Грегори

**Библиография**
- Harry Percival, Bob Gregory. *Architecture Patterns with Python: Enabling Test-Driven Development, Domain-Driven Design, and Event-Driven Microservices*. O'Reilly, 2020. ISBN 978-1492052203. Бесплатно онлайн: https://www.cosmicpython.com (CC BY-NC-ND).
- Рус. изд.: *Паттерны разработки на Python: TDD, DDD и событийно-ориентированная архитектура*. СПб.: Питер, 2022.

**Ключевые принципы**
1. **Доменная модель на чистом Python** (dataclasses), без зависимостей от ORM.
2. **Инверсия ORM:** классическое (императивное) отображение — ORM зависит от модели, а не наоборот.
3. **Repository** как абстракция хранилища + **FakeRepository** для быстрых тестов.
4. **Service Layer** (use cases) — точка входа для оркестрации; тесты пишутся преимущественно против него («high gear»).
5. **Unit of Work** — атомарность и владение транзакцией как контекстный менеджер.
6. **Агрегаты и оптимистичная блокировка** через номер версии.
7. **Доменные события и шина сообщений (message bus)** внутри процесса.
8. **Команды против событий:** команда — одному обработчику, может упасть; событие — многим, публикуется «в пустоту».
9. **Внешние события** через брокер (Redis pub/sub в книге) для интеграции сервисов.
10. **CQRS:** чтения — простыми SQL-запросами/представлениями.
11. **Внедрение зависимостей и bootstrap-скрипт** (composition root).
12. **Тестовая пирамида:** много юнит-тестов домена и сервисного слоя с фейками, мало e2e.

**Применение в NotaCode**
- **Эталон структуры бэкенда** — эта книга, адаптированная под FastAPI: `domain/model.py` (dataclasses, `frozen=True` для VO), `adapters/orm.py` (imperative mapping SQLAlchemy `registry.map_imperatively`), `adapters/repository.py`, `service_layer/unit_of_work.py`, `service_layer/handlers.py`, `service_layer/messagebus.py`, `bootstrap.py`, `entrypoints/fastapi_app.py`.
- **Команды и события:** `CommitVersion`, `RollbackToVersion`, `RequestExport`, `SyncToGitHub` — команды (один обработчик, ошибка → HTTP-ответ); `VersionCommitted` → обработчики `enqueue_autosync`, `invalidate_preview_cache`.
- **FakeUnitOfWork + FakeRepository** — основа быстрых тестов use case-ов; интеграционные тесты с реальной PostgreSQL (testcontainers) — только для адаптеров.
- **DI:** `bootstrap(uow=..., publisher=..., renderer=...)` собирает обработчики с частичным применением зависимостей; FastAPI `Depends` только в entrypoints.
