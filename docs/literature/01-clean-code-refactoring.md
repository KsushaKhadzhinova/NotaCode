# 01. Чистый код, рефакторинг, TDD, паттерны проектирования

> Конспекты написаны своими словами. Цитаты — не длиннее 15 слов и не больше одной на книгу.
> Раздел «Применение в NotaCode» — это обязательные правила для кода фронтенда (TypeScript/React) и бэкенда (Python/FastAPI).

## 1. Clean Code — Роберт Мартин

**Библиография**
- Robert C. Martin. *Clean Code: A Handbook of Agile Software Craftsmanship*. Prentice Hall, 2008. ISBN 978-0132350884.
- Рус. изд.: Роберт Мартин. *Чистый код. Создание, анализ и рефакторинг*. СПб.: Питер, 2010 (переиздания 2013, 2019).

**Ключевые принципы**
1. **Имена раскрывают намерение.** Имя переменной, функции или класса должно объяснять, зачем она существует, что делает и как её использовать. Если имя нужно пояснять комментарием, имя плохое.
2. **Функции маленькие и делают одно дело.** Одна функция — один уровень абстракции. Если из функции можно выделить другую с осмысленным именем, значит она делала больше одного дела.
3. **Правило понижения (Stepdown Rule).** Код читается сверху вниз как рассказ: каждая функция ведёт к функциям следующего, более низкого уровня абстракции.
4. **Мало аргументов.** Идеал — 0–2 аргумента; 3 требуют обоснования; больше — признак, что нужен объект-параметр. Флаговые булевы аргументы запрещены: они означают, что функция делает два дела.
5. **Отсутствие побочных эффектов и разделение команд и запросов (CQS).** Функция либо меняет состояние, либо возвращает значение — не оба сразу.
6. **Исключения вместо кодов ошибок.** Обработка ошибок — отдельная ответственность; блок try выносится в отдельную функцию. Не возвращать и не передавать `null`.
7. **Комментарии — признак неудачи выразить мысль кодом.** Хороший код самодокументирован; комментарии устаревают и лгут. Допустимы лишь юридические заголовки и пояснения к внешним контрактам (у нас — не допускаются вовсе, см. ниже).
8. **Форматирование как коммуникация.** Вертикальная плотность, близость связанных понятий, газетная метафора (важное сверху, детали ниже).
9. **Объекты против структур данных.** Объекты скрывают данные и открывают поведение; структуры данных открывают данные и не имеют поведения. Закон Деметры: не разговаривать с «чужими» объектами через цепочки вызовов.
10. **Границы.** Сторонний код оборачивается адаптером; тесты-исследования (learning tests) фиксируют поведение внешней библиотеки.
11. **Чистые тесты (F.I.R.S.T.).** Быстрые, независимые, повторяемые, самопроверяемые, своевременные. Один концепт на тест; тестовый код так же чист, как боевой.
12. **Классы маленькие, с одной причиной для изменения (SRP)** и высокой связностью (cohesion).
13. **Эмерджентный дизайн по Кенту Беку:** проходят все тесты → нет дублирования → выражает намерение → минимум классов и методов.
14. **Правило бойскаута.** Код после изменения оставляется чище исходного состояния.

Цитата: «The only valid measurement of code quality: WTFs/minute» (Р. Мартин, эпиграф к книге).

**Применение в NotaCode**
- **Ноль комментариев** в `*.py`, `*.ts`, `*.tsx`. Контролируется линтером: `eslint-plugin` с правилом `no-warning-comments` + кастомное правило запрета `//` и `/* */` (кроме директив `@ts-expect-error` с обоснованием в PR, а не в коде); для Python — `ruff` + собственная проверка токенайзером (`tokenize.COMMENT`) в pre-commit. Docstring-и также запрещены; публичные контракты документируются через OpenAPI (Pydantic `Field(description=...)`) и в `docs/`.
- **Размер функции:** ≤ 20 строк тела, цикломатическая сложность ≤ 5 (`ruff` правило `C901` с `max-complexity = 5`, `eslint complexity: 5`), вложенность ≤ 2.
- **Аргументы:** ≤ 3 позиционных; булевы флаги запрещены — вместо `render(diagram, true)` два метода `renderPreview`/`renderFull` или enum-стратегия.
- **Размер файла:** ≤ 200 строк; класс/модуль — одна причина для изменения.
- **Именование:**
  - Python: `snake_case` функции, `PascalCase` классы, `UPPER_SNAKE` константы; булевы — `is_`/`has_`/`can_`; функции — глаголы (`parse_source`, `validate_bpmn_gateway`), классы — существительные (`DiagramRepository`, `PetriNetValidator`).
  - TypeScript: `camelCase`/`PascalCase`, React-компоненты — существительные (`DiagramCanvas`), хуки — `useXxx`, обработчики — `handleXxx`, пропсы-колбэки — `onXxx`.
  - Запрещены сокращения кроме доменных (`bpmn`, `erd`, `idef0`, `dfd`, `uml`, `ast`, `dsl`), запрещены «шумовые» суффиксы `Manager`, `Data`, `Info`, `Helper`, `Util`.
- **Без `null`-протоколов:** в Python — `Optional` только на границах, внутри домена — Null Object или исключение; в TS — `strictNullChecks`, discriminated unions (`Result<T, E>`).
- **Внешние библиотеки** (Lark, maxGraph/elkjs, Monaco, PyGithub, Google Drive API) — только через адаптеры в слое инфраструктуры, с learning-тестами.
- **CQS** в сторах Zustand: действия (`addNode`) ничего не возвращают, селекторы (`selectNodeById`) не мутируют.

## 2. The Pragmatic Programmer — Эндрю Хант, Дэвид Томас

**Библиография**
- Andrew Hunt, David Thomas. *The Pragmatic Programmer: From Journeyman to Master*. Addison-Wesley, 1999.
- 2-е изд.: *The Pragmatic Programmer: Your Journey to Mastery, 20th Anniversary Edition*. Addison-Wesley, 2019. ISBN 978-0135957059.
- Рус. изд.: *Программист-прагматик. Путь от подмастерья к мастеру*. М.: Лори, 2004; *Программист-прагматик. 2-е юбилейное издание*. М.: Диалектика, 2020.

**Ключевые принципы**
1. **DRY — не повторяйся.** Каждое знание должно иметь единственное авторитетное представление. Речь о знании, а не о тексте: две одинаковые строки с разным смыслом — не дублирование.
2. **Ортогональность.** Изменение одного компонента не затрагивает другие; снижает риски и упрощает тестирование.
3. **Обратимость.** Нет окончательных решений; архитектура должна позволять сменить БД, облако, поставщика.
4. **Трассирующие пули (tracer bullets).** Сначала тонкий сквозной работающий срез через все слои, затем наращивание.
5. **Прототипы — выбрасываемые**, в отличие от трассирующих пуль.
6. **Предметно-ориентированные языки.** Программируйте близко к предметной области; мини-языки — законный инструмент.
7. **Оценка сроков** — итеративно, с указанием единиц точности.
8. **Простой текст и командная оболочка** как универсальные инструменты; всё под контролем версий.
9. **Проектирование по контракту и «падай рано» (crash early).** Мёртвая программа вредит меньше, чем повреждённая.
10. **Утверждения (assertions)** о невозможном; ресурсы освобождает тот, кто их выделил.
11. **Разрыв связей (decoupling), «Скажи, не спрашивай»,** избегание цепочек вызовов.
12. **Не программируйте по совпадению.** Понимайте, почему код работает.
13. **Беспощадное и непрерывное тестирование,** тесты — первые пользователи кода; автоматизация всего.
14. **Теория разбитых окон** — не оставлять плохой код без исправления.
15. **ETC (Easier To Change)** — главный критерий хорошего дизайна во 2-м издании.

Цитата: «Good design is easier to change than bad design» (Хант и Томас, 2-е изд.).

**Применение в NotaCode**
- **DRY для знаний о нотациях:** метамодель каждой нотации (типы элементов, допустимые связи, кратности) описывается один раз — декларативно в `backend/app/notations/<notation>/metamodel` — и из неё генерируются: правила валидатора, палитра холста, подсказки автодополнения Monaco, JSON Schema для фронта. Ручное дублирование списков элементов на фронте запрещено.
- **Tracer bullet MVP:** первый сквозной срез — DSL `flowchart` (free-form) → парсер → AST → layout → SVG на холсте → сохранение в PostgreSQL → история версий. Остальные нотации подключаются как плагины к уже работающему конвейеру.
- **Обратимость хранилищ:** порт `DiagramStorage` с адаптерами `PostgresStorage`, `LocalDeviceStorage` (IndexedDB/File System Access API), `GitHubStorage`, `GoogleDriveStorage`; смена провайдера не затрагивает домен.
- **Crash early:** валидация входа Pydantic на границе; внутри домена — инварианты, нарушение → доменное исключение → HTTP 422/409 через единый обработчик.
- **ETC** — критерий на code review: «станет ли это проще менять?».
- **Всё в тексте и под Git:** диаграммы хранятся как исходник DSL (текст), а не как бинарная картинка; это и делает diff/rollback дешёвыми.

## 3. Refactoring, 2nd Edition — Мартин Фаулер

**Библиография**
- Martin Fowler (with Kent Beck). *Refactoring: Improving the Design of Existing Code*. 2nd ed. Addison-Wesley, 2018. ISBN 978-0134757599. (1-е изд. — 1999, на Java; 2-е — на JavaScript.)
- Рус. изд.: Мартин Фаулер. *Рефакторинг кода на JavaScript: улучшение проекта существующего кода*. 2-е изд. М.: Диалектика/Вильямс, 2019. 1-е изд.: *Рефакторинг. Улучшение существующего кода*. СПб.: Символ-Плюс, 2003.

**Ключевые принципы**
1. **Рефакторинг — изменение структуры без изменения наблюдаемого поведения,** маленькими шагами, каждый из которых оставляет систему рабочей.
2. **Две шляпы:** в каждый момент либо добавляешь функциональность, либо рефакторишь — не одновременно.
3. **Самотестирующийся код** — необходимое условие рефакторинга.
4. **Правило трёх:** на третий раз похожего кода — рефакторить.
5. **Подготовительный рефакторинг:** «сделай изменение простым, затем сделай простое изменение».
6. **Запахи кода:** загадочное имя, дублирование, длинная функция, длинный список параметров, глобальные данные, изменяемые данные, расходящиеся модификации, «стрельба дробью», завистливая функция, группы данных, одержимость примитивами, повторяющиеся switch, цепочки сообщений, посредник, большой класс, отказ от наследства, комментарии.
7. **Базовые приёмы:** Extract Function, Inline Function, Extract Variable, Change Function Declaration, Encapsulate Variable, Rename Variable, Introduce Parameter Object, Combine Functions into Transform, Split Phase.
8. **Split Phase** — разделение вычисления на последовательные фазы с промежуточной структурой данных (применяется в компиляторах).
9. **Replace Conditional with Polymorphism** и **Replace Primitive with Object**.
10. **Инкапсуляция коллекций и записей;** избегать изменяемых разделяемых данных, предпочитать неизменяемые значения.
11. **Separate Query from Modifier**, **Remove Flag Argument**, **Replace Parameter with Query**.
12. **Рефакторинг и производительность:** сначала ясный код, потом профилирование и оптимизация «горячих» мест.
13. **Рефакторинг непрерывен и встроен в ежедневную работу,** а не отдельная задача в бэклоге.

Цитата: «Any fool can write code that a computer can understand» (М. Фаулер).

**Применение в NotaCode**
- **Split Phase как архитектура компилятора DSL:** `lex → parse → build AST → resolve names → semantic validation → lower to Diagram Model → layout → render`. Каждая фаза — отдельный модуль с неизменяемой входной/выходной структурой (`frozen dataclass` / `readonly` типы).
- **Replace Conditional with Polymorphism:** никаких `if notation == "bpmn"` в ядре. Реестр `NotationPlugin` с методами `metamodel()`, `validators()`, `autofixes()`, `layout_strategy()`, `exporters()`.
- **Replace Primitive with Object:** `DiagramId`, `VersionId`, `NodeId`, `NotationKind`, `Point`, `Bounds` — value objects, не `str`/`int`/`tuple`.
- **Запахи как чек-лист ревью:** PR с длинной функцией, флаговым аргументом, `switch` по типу нотации, изменяемым глобальным состоянием отклоняется.
- **Две шляпы в Git:** коммиты рефакторинга (`refactor:`) и функциональности (`feat:`) не смешиваются (Conventional Commits).
- **Автоматический рефакторинг** доступен и пользователю в IDE: переименование элемента диаграммы через LSP `textDocument/rename` обновляет все ссылки в DSL.

## 4. Test-Driven Development: By Example — Кент Бек

**Библиография**
- Kent Beck. *Test-Driven Development: By Example*. Addison-Wesley, 2002 (copyright 2003). ISBN 978-0321146533.
- Рус. изд.: Кент Бек. *Экстремальное программирование: разработка через тестирование*. СПб.: Питер, 2003.

**Ключевые принципы**
1. **Красный — зелёный — рефакторинг.** Падающий тест → минимальный код для прохождения → устранение дублирования.
2. **Не писать боевой код без падающего теста.**
3. **Маленькие шаги,** размер которых регулируется уверенностью: при неуверенности — мельче.
4. **Список тестов (test list)** как рабочий план сессии.
5. **Fake It ('Til You Make It)** — сначала вернуть константу, затем обобщить.
6. **Триангуляция** — обобщать, только когда два примера требуют этого.
7. **Очевидная реализация** — если решение очевидно, пиши его сразу.
8. **Тест пишется первым, assert — первым внутри теста** (от желаемого результата назад).
9. **Изолированные тесты:** порядок запуска не важен, нет общего изменяемого состояния.
10. **Тестовые данные должны быть очевидными;** «Evident Data» — видно связь входа и выхода.
11. **Паттерны:** Child Test, Mock Object, Self Shunt, Log String, Crash Test Dummy, Broken Test (оставить падающий тест в конце дня, чтобы знать, где продолжить).
12. **TDD снижает страх** и создаёт исполнимую спецификацию.
13. **Устранение дублирования между тестом и кодом** — движущая сила дизайна.

Цитата: «Clean code that works» — цель TDD по Беку.

**Применение в NotaCode**
- **100% покрытие — следствие TDD, а не цель ради цифры.** В CI: `pytest --cov=app --cov-branch --cov-fail-under=100`, `vitest --coverage` с порогом 100% по statements/branches/functions/lines. Исключения из покрытия (`pragma: no cover`) запрещены — это тоже комментарий.
- **Для каждого правила валидатора** — пара тестов: «модель нарушает правило → ошибка с кодом `BPMN-GW-001`» и «модель корректна → нет ошибки»; для каждого autofix — тест «до/после» + тест идемпотентности (повторное применение не меняет результат).
- **Грамматика DSL — через golden-тесты:** `tests/fixtures/<notation>/*.nota` → ожидаемый AST (snapshot в JSON). Изменение снапшота требует явного ревью.
- **Property-based тесты** (Hypothesis, fast-check) для парсер ↔ принтер: `parse(print(ast)) == ast` (round-trip), для diff: `apply(diff(a, b), a) == b`.
- **Evident Data:** фабрики тестовых данных (`factory_boy`, билдеры в TS) с говорящими именами: `a_bpmn_process().with_exclusive_gateway_without_default().build()`.
- **Test list** ведётся в задаче (issue), а не в коде.

## 5. Design Patterns (GoF) — Гамма, Хелм, Джонсон, Влиссидес

**Библиография**
- Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides. *Design Patterns: Elements of Reusable Object-Oriented Software*. Addison-Wesley, 1994. ISBN 978-0201633610.
- Рус. изд.: Э. Гамма, Р. Хелм, Р. Джонсон, Дж. Влиссидес. *Приёмы объектно-ориентированного проектирования. Паттерны проектирования*. СПб.: Питер, 2001 (многократно переиздавалась).

**Ключевые принципы**
1. **Программируйте на уровне интерфейсов, а не реализаций.**
2. **Предпочитайте композицию наследованию.**
3. **Инкапсулируйте то, что меняется.**
4. **Порождающие паттерны:** Abstract Factory, Builder, Factory Method, Prototype, Singleton (последний — осторожно, это глобальное состояние).
5. **Структурные:** Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy.
6. **Поведенческие:** Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor.
7. **Паттерн = имя + проблема + решение + последствия;** описание компромиссов не менее важно, чем решение.
8. **Composite** — единообразная работа с деревом частей и целого.
9. **Visitor** — добавление операций над стабильной иерархией классов без её изменения.
10. **Command + Memento** — отмена/повтор действий и снимки состояния.
11. **Interpreter** — представление грамматики простого языка классами.
12. **Observer** — оповещение подписчиков об изменении состояния.
13. **Паттерны — словарь команды,** а не цель; применять, когда есть сила, которую паттерн уравновешивает.

**Применение в NotaCode**
| Паттерн | Где используется |
|---|---|
| Composite | Модель диаграммы: `Diagram → Container (pool/lane/package/subprocess) → Node/Edge`; вложенные подпроцессы BPMN, пакеты UML, декомпозиция IDEF0 (A0 → A1…) |
| Visitor | Обход AST DSL: `ValidationVisitor`, `LoweringVisitor` (AST → модель), `PrettyPrintVisitor`, экспортеры (`BpmnXmlExporter`, `PnmlExporter`, `XmiExporter`, `SvgExporter`). В Python — `functools.singledispatchmethod` или match по типу узла |
| Strategy | Алгоритмы раскладки (layered/Sugiyama, orthogonal, force-directed, tree), выбор по нотации |
| Command | Все правки на холсте (`MoveNodeCommand`, `ConnectCommand`) → стек undo/redo и двусторонняя синхронизация холст ↔ DSL |
| Memento | Снимки для истории версий на клиенте; на сервере — неизменяемые версии |
| Observer | Подписки Zustand, события домена на бэкенде (`DiagramSaved`, `VersionCreated`) |
| Abstract Factory | `NotationPlugin` поставляет согласованное семейство: метамодель + валидаторы + фабрику фигур + экспортеры |
| Adapter | Хранилища (GitHub, Google Drive, IndexedDB), провайдеры AI (сейчас — `StubAiAssistant`) |
| Facade | `DiagramCompiler.compile(source) -> CompilationResult` скрывает все фазы |
| Chain of Responsibility | Конвейер autofix и middleware FastAPI (auth → rate limit → correlation id) |
| State | Состояния инструмента холста (выделение, соединение, панорамирование) |
| Flyweight | Общие определения стилей фигур для тысяч узлов |
| Singleton | **Запрещён** как класс; единственные экземпляры — только через DI-контейнер FastAPI `Depends` |
