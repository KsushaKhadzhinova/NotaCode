# NotaCode — спецификация требований (живой SRS)

**Статус:** черновик v0.1, живой документ. Ведётся в Git, меняется по мере ответов на открытые вопросы.
**Дата:** 2026-09-23
**Язык:** русский (термины интерфейса и стандартов — в оригинале).

NotaCode — веб-приложение (PWA) для моделирования структур и процессов в режиме «diagram as code»: пользователь пишет код диаграммы на собственном DSL, система проверяет его по правилам выбранной нотации (UML, ERD, IDEF0/IDEF1X/IDEF3, DFD, позже BPMN, сети Петри и произвольные диаграммы), рендерит диаграмму на канвасе, хранит её, ведёт версии и помогает AI-ассистентом. Интерфейс построен по образцу VS Code (код) и draw.io (канвас).

## 2. Источники и как на них ссылаться

Каждое требование ссылается на источник. Используются такие коды:

| Код | Источник | Как читать ссылку |
|---|---|---|
| `WL:Lnn` | [`../source-materials/user-wishlist-mvp.md`](../source-materials/user-wishlist-mvp.md). Исходник: `мне нужно чтобы было.txt` | `nn` — номер строки исходного .txt, он же указан в md-файле в квадратных скобках `[Lnn]` |
| `TZ:Lnnnn` | [`../source-materials/tz-full-chat-and-labs.md`](../source-materials/tz-full-chat-and-labs.md). Исходник: `проанализируй полученную информацию.txt` | `nnnn` — номер строки исходного .txt. Опорные диапазоны: идея проекта — L5–91; ответ ассистента про архитектуру — L91–159; план разработки — L159–248; стек «React + PWA, Python» — L254; лабораторные — L552–3453; описание системы — L3506–3714; ранние FR/NFR/UC — L3714–4061; **итоговые пожелания пользователя — L4061–4095** |
| `KR:§…` | [`../source-materials/kursach.md`](../source-materials/kursach.md). Исходник: `Курсач.docx` | Раздел документа: «Инструменты», «Диаграммы», «План», «лр 3 4» |
| `BRIEF` | Постановка задачи аналитику от 2026-09-23: каталог нотаций, NFR по качеству кода, интеграции, модель «Run vs авторендер», модель автосохранения | Требования пользователя, переданные через основного ассистента |
| `OLD:<файл>` | `E:\VisualDSL-Platform\docs\…`, документация предыдущей попытки (DiagramCode). **Может содержать ошибки**: используется только как вход, решения оттуда считаются неподтверждёнными, пока пользователь их не подтвердит (см. [06-open-questions.md](06-open-questions.md)) | Путь к файлу относительно `docs/` старого проекта |

Приоритет источников при конфликте, пока пользователь не ответил: `BRIEF` → `TZ:L4061–4095` (самые поздние пожелания) → `WL` → остальной `TZ` → `KR` → `OLD`. Все найденные конфликты вынесены в [06-open-questions.md](06-open-questions.md) и **не считаются решёнными** до ответа пользователя.

## 3. Приоритеты

| Метка | Значение |
|---|---|
| **MVP** | Входит в первую выпускаемую версию |
| **Post-MVP** | Следующие версии. Архитектура MVP должна допускать добавление без переделки |
| **MVP (?)** | Источники расходятся. Приоритет предварительный, ссылка на вопрос `Q-nn` |

## 4. Нумерация

- `FR-nnn`: функциональные требования (номера не переиспользуются; удалённые помечаются «снято»).
- `NFR-nnn`: нефункциональные требования.
- `UC-nn`: сценарии использования.
- `V-<нотация>-nn`: правила валидации нотаций (в [03-notations-catalog.md](03-notations-catalog.md)).
- `AF-<нотация>-nn`: кандидаты автоисправления.
- `Q-nn`: открытые вопросы.

## 5. Глоссарий

| Термин | Определение |
|---|---|
| **NotaCode** | Рабочее название продукта (в источниках также: «Visual DSL Diagrammer», «DiagramCode», «Веб-приложение генерации диаграмм»; см. Q-40) |
| **DSL NotaCode** | Собственный текстовый язык описания диаграмм. Один язык на все нотации; допустимый набор элементов определяется объявленной нотацией и типом диаграммы |
| **Нотация** | Стандарт или методология графического моделирования: UML, BPMN, ERD, IDEF0, IDEF1X, IDEF3, DFD, сети Петри, «без нотации» (произвольная диаграмма) |
| **Тип диаграммы** | Вид диаграммы внутри нотации: например, UML → class, sequence; BPMN → collaboration |
| **Уровень / вариант** | Уточнение типа: уровень модели (ERD: концептуальный/логический/физический), графический стиль (ERD: Chen/Crow's Foot/UML), разновидность (DFD: Gane–Sarson/Yourdon–DeMarco; сети Петри: цветные/временные…) |
| **Ключ нотации** | Машинный идентификатор цепочки «нотация.тип.вариант», например `erd.logical.crowsfoot`, `uml.sequence`, `idef0.decomposition` |
| **Профиль нотации** | Модуль-плагин, который для ключа нотации определяет элементы, допустимые связи, правила валидации, автоисправления, раскладку, рендер и форматы экспорта |
| **Внутренняя модель** | Нотация-независимый типизированный граф (узлы, рёбра, контейнеры, атрибуты, позиции в исходном коде), в который разбирается DSL |
| **Канвас** | Область отображения диаграммы (в духе draw.io): масштаб, панорамирование, сетка, выделение, в будущем визуальное редактирование |
| **Run** | Явный запуск разбора, валидации и рендера кнопкой или горячей клавишей |
| **Авторендер** | Режим, в котором рендер запускается автоматически после изменения кода (с задержкой debounce) |
| **Автосохранение** | Автоматическое сохранение кода и состояния диаграммы в последнюю цель и последний формат сохранения |
| **Цель сохранения** | Куда сохраняется работа: база данных (аккаунт), устройство, Git/GitHub, Google Drive |
| **Формат** | Представление при сохранении или экспорте: Canvas, SVG, PNG, XML, файл нотации, файл кода, файл проекта (см. FR-группу «Форматы») |
| **Проект** | Единица работы, которую пользователь открывает целиком. В MVP открыт ровно один проект. Состав проекта см. Q-16 |
| **Шаблон** | Встроенный пример кода диаграммы для конкретной нотации и типа. Шаблон только для чтения: его просматривают, копируют или вставляют в свой файл |
| **Версия** | Неизменяемый снимок кода (и метаданных) диаграммы, созданный при сохранении |
| **Diff** | Сравнение двух версий: построчное текстовое и (позже) визуальное |
| **Откат (rollback)** | Создание новой версии с содержимым выбранной старой версии; история при этом не теряется |
| **Undo / Redo** | Отмена и повтор правок в текущей сессии (Ctrl+Z / Ctrl+Y) |
| **Валидация** | Проверка синтаксиса DSL и правил нотации. Итог — диагностики уровней Error / Warning / Info |
| **Диагностика** | Одно сообщение валидации: код правила, уровень, текст, позиция (строка, колонка), связанный элемент диаграммы |
| **Автоисправление (autofix)** | Предлагаемое системой детерминированное исправление диагностики (quick fix), применяемое по подтверждению |
| **Кросс-подсветка** | Двусторонняя связь «строки кода ↔ элемент канваса»: наведение или выделение с одной стороны подсвечивает соответствующее с другой |
| **Движок рендеринга (engine)** | Внешняя или встроенная система, которая строит изображение: встроенный рендерер NotaCode, PlantUML, Mermaid, Graphviz, D2, Kroki, draw.io и т. п. |
| **Activity bar** | Вертикальная панель иконок разделов (как в VS Code): шаблоны, файлы/поиск, отладка, терминал, статус, расширения, профиль |
| **Status bar** | Нижняя строка состояния: ошибки/предупреждения, цель пуша, язык, Ln/Col, отступы, язык приложения, уведомления, кодировка, время последнего сохранения и пуша |
| **Тост** | Всплывающее временное уведомление типа Error / Warning / OK |
| **Нижняя панель** | Панель с вкладками Terminal и Problems |
| **AI-ассистент** | Модуль генерации и исправления кода через LLM API. Режимы: «Написать код», «Исправить код», «Исправить ошибку», «Спросить по документации». В текущей реализации — заглушка (stub) |
| **Stub-провайдер** | Реализация AI-интерфейса без сетевых вызовов, возвращает предсказуемый результат |
| **PWA** | Progressive Web App: установка приложения, офлайн-работа через Service Worker, локальное хранилище (IndexedDB) |
| **ICOM** | IDEF0: Input, Control, Output, Mechanism — роли стрелок по сторонам блока |
| **UOW** | IDEF3: Unit of Work, единица работы |
| **PFDD / OSTN** | IDEF3: Process Flow Description Diagram / Object State Transition Network |
| **BNF** | Бэкуса–Наура форма; в DFD применяется для словаря данных |
| **CRUDL** | Create, Read, Update, Delete, List: полный набор операций над элементами |
| **Post-MVP** | Всё, что идёт после первой выпускаемой версии |
